## A. 安全边界（T0）

### A1 传输面零鉴权 + 默认全网卡监听 + WS 无 Origin 校验 → 跨边界接管宿主
- **位置**：`ac-web-server/src/service.ts:100`（缺省 `host: '::'`）、`:407-421`
  （handleConnection 不校验 Origin/Host/token）；`cordis.yml:109-115` 只配 port；
  `ac-web-api/src/index.ts`（70 个 RPC 全零鉴权）。
- **可达面**：
  - LAN 内任意主机直连 3830 即全权（`::` = 双栈全网卡）；
  - 恶意网页 `new WebSocket('ws://127.0.0.1:3830')`（WS 不受 CORS 约束、
    无 Origin 校验；http 页面 / DNS rebinding 可绕混合内容限制）；
  - `plugin/load`（web-api:1285-1300）接受**任意绝对 dir + 调用方自报 grants**
    → 动态 import（tsx 下 TS/JS 通吃）= 进程内任意代码；
  - `agents/create` 白名单含 `tags`/`settings`（agent-admin service.ts:28-42）→
    建式 `tags:['admin']` 或 `settings.security.workdir='C:\'` 的全权 Agent；
  - HTTP 面同病：`POST /api/workspaces` 注册任意本机路径为根 →
    `GET /api/workspace/raw` 任意文件读、`POST /api/upload` 任意写。
- **攻击链**：恶意页 WS 连入 → `events/policy-set` 停掉 ac-security 监听 或直接
  建 admin Agent → `conversation/deliver` 驱动 bash → 主机接管。
- **修复方向**：缺省 host 改 `127.0.0.1`（yml 显式）；WS upgrade 校验 Origin
  白名单 + Host；写面 RPC（plugin/agents/config/market/system/upload/workspaces）
  加一次性启动 token；`plugin/load` 的 grants 不得取自调用方参数。
- **验证**：主线亲验（web-server service.ts / web-api index.ts / agent-admin
  service.ts / cordis.yml）。

### A2 ac-math node:vm 沙箱逃逸 → 任意 Agent（含默认预设）宿主 RCE / 事件循环冻结【实测】
- **位置**：`ac-math/src/index.ts:14-37,46`。
- **双通道**：
  1. **同步逃逸（已实测 PoC，Node v24.18.0）**：宿主对象（Math/JSON/Number/
     parseFloat…）按引用注入 vm context → `Math.constructor.constructor("return
     process")()` 经宿主 Function 构造器直达 `process` → child_process 任意命令。
     timeout 只限同步执行，逃逸载荷本身同步——兜底无效。
  2. **异步冻结**：`Promise.resolve().then(()=>{while(true){}})` 的回调进宿主
     微任务队列，vm watchdog 管不到 → 事件循环永久冻结，全宿主假死且无信号可救。
- **可达性**：math 注册**无 requiredTags**（全库仅 7 处工具有标签）——一切 Agent
  含 `__standard__` 默认预设可用；提示注入（网页内容/搜索结果/文件）→ 一次 math
  调用即中，**整体绕过能力门禁/路径沙箱/命令扫描三层设计**。
- **修复方向**：弃 vm 直求值，换纯表达式解析器（自写 parser / expr-eval）；
  若保留 vm，context 内不得出现任何宿主对象（只放纯数据副本）+
  `--disallow-code-generation-from-strings`；正确隔离是 worker_threads + terminate。
- **验证**：子代理实测 PoC + 主线亲读确认注入面。

### A3 凭据窃取全链 → 全部 API key 失守
- **五环相扣**（各环独立成立，链条整体可达）：
  1. bash 工具无 requiredTags（`ac-shell-tools/src/index.ts:87-100`）——所有
     Agent 默认可执行命令；
  2. 命令扫描结构性绕过：写脚本再执行（`write x.js` → `node x.js` 命令行无路径
     特征放行）、`~/` 前缀不检（bash-scan.ts:85/110）、`%USERPROFILE%`/`$env:`
     隐藏目标；
  3. `credentials.json`/`config.json` 不在控制面 deny 黑名单
     （ac-security index.ts:44-50、ac-sandbox-core paths.ts:18-26）——预设 Agent
     沙箱=数据根（workspace index.ts:218）可用 `read` 直读凭据库；
  4. 加密密钥 = PBKDF2(`hostname:username`) **零秘密成分**
     （ac-credentials service.ts:35-40）——任何本地脚本可离线解密全部 key；
  5. 输出脱敏可绕：脚本内 `Buffer.from(key).toString('base64')` 后打印——精确值
     与 sk- 模式全失效，编码态明文进上下文可外传。
- **修复方向**：credentials.json/config.json 并入 denyPaths 绝对路径注入；bash
  至少挂 `dev` requiredTags；machineKey 引入真秘密（DPAPI/Keychain/用户口令）；
  脱敏补 base64/hex 长串启发。
- **验证**：主线亲验 requiredTags 全库 grep + 黑名单清单 + 密钥派生。

## B. 数据完整性（T0）

### B1 compact/归档窗口静默丢用户消息
- **位置**：`ac-session/src/index.ts:805-814,822-834` + `ac-archive/src/service.ts:565-598`
  （同款窗口：`ac-group/src/service.ts:404`、session `deleteMessage/truncateAfter`）。
- **时序**：archiveAndRebuild 在 T0 读 records 快照 →（多个 await 边界）→
  `session.compact`：内部 `await flush()` 把窗口内新到消息**写进文件** →
  `rewriteMessages` 用 T0 快照的 keep tmp+rename **覆盖文件** + `queues.delete`
  → 先 durable 又被抹掉，`seen` WeakSet 一并作废，零日志。
- **现实触发**：归档整理 run 期间（可达分钟级）用户消息经 busy→steer 默认路径
  注入并落账；或群桶其他成员并发发言。归档恰在长对话高流量时触发。
- **修复方向**：rewriteMessages 前重读当前文件行合并入 keep；或 per-conversation
  互斥 + compact 内二次合并。
- **验证**：主线亲验完整时序（steer 落账路径 + compact 内部 flush 顺序）。

### B2 credentials.json 非原子全量重写 → 撕裂后全量凭据永久丢失
- **位置**：`ac-credentials/src/service.ts:152-164`（全仓 owning service 中唯一
  裸 `writeFileSync` 全量重写，无 tmp+rename）；`:136-150`（readStore 解析失败
  catch → `{}`；解密失败条目静默丢弃）。
- **时序**：写盘中途崩溃/断电 → 文件撕裂 → 下次 boot readStore 归空 → 用户任设
  一键 → writeKey 把空态全量落盘 → **旧凭据不可恢复**。解密失败丢弃路径同病。
- **修复方向**：改 tmp+rename 原子写（+fsync）；解密失败条目保留密文形态落盘。
- **验证**：主线亲验。

### B3 JSONL 半行崩溃残留 → 后续一次丢两行 + seq 重置级联
- **位置**：`ac-session/src/index.ts:656-665`（write 无前导换行保护）、
  `:748-784`（读侧跳过损坏行不修复）、`:601-612`（probeNextSeq 末行解析失败
  → catch 返回 1）。
- **时序**：writeSync 中途崩溃 → 尾部无 `\n` 半行 → 重启后下一次 append 直接
  拼接 → `<半行><新完整行>` 同行 → 读取跳过 = **两行俱损**；probeNextSeq 重置
  1 → 与既有 seq 冲突 → `ac-archive-core` dedupCutoff 按 seq first-match 取错
  cutoff → 二次归档区间错位（幂等破坏）。
- **修复方向**：建队/启动时检测并截断尾部半行（末行无换行且不可解析即修复）；
  probeNextSeq 解析失败全文件扫描最大 seq。
- **验证**：主线亲验 write/probe 代码 + 子代理验 archive-core 消费面。

### B4 双实例互斥失效 → 同数据根双写者静默共存

## C. 进程稳定性（T0）

### C1 emit 无监听器隔离 + 全仓无进程级兜底 → 单点故障放大为宿主崩溃/落账饿死
- **位置**：vendor `src/vendor/cordis/src/events.ts:200-202`（emit 同步 map 调用、
  异步 rejection 悬空）；preview 无任何 `unhandledRejection/uncaughtException`
  处理器（对照旧轨 src/bootstrap.ts:53-58 有）。
- **已实锤向量**（四条，均亲验）：
  1. `ac-singles/src/service.ts:90-91`——`void this.maybeGenerateTitle(...)` 无
     catch，`update()` 落盘（裸 writeFileSync，Windows AV 锁/盘满可抛）在
     try/finally 之外 → 标题生成这个装饰性功能可崩宿主；
  2. `ac-plugin-registry/src/index.ts:297-303`——`void loadInstalled().then(...)`
     无 catch → registry.json 损坏即崩（见 C2）；
  3. `ac-jobs/src/service.ts:127,151-158`——`void job.cancel()` 与 settle 内
     emit 的异步 rejection 悬空；
  4. `ac-tools/src/service.ts:67-70` + shell-tools `onData`——bash 流式输出的
     `tool/progress` emit 若任一订阅者同步 throw = uncaughtException（子进程
     stdout 回调里，高频主路径）。
- **次生面**：emit 同步 throw 还会**跳过同事件后续监听器**——ac-session 落账
  监听器可被饿死（会话历史静默缺失）；`loop/after-run`（agent-loop :358）在
  try 外抛 = 已完成 run 的结果丢失。M23 Agent 自开发插件的 emit 监听器 bug
  使触发人群常态化。
- **修复方向**：宿主入口装进程级兜底（记日志不退出）；vendor emit 逐回调
  try/catch（对齐同库 emitPluginDisposed 已有实现）；四处实锤点补 catch。
- **验证**：主线亲验全部四向量 + vendor 源码。

### C2 plugins/registry.json 损坏 → 崩溃循环至熔断，无 fail-soft
- **位置**：`ac-plugin-core/src/store.ts:117-129`（readRegistry 三个状态文件中
  唯一 fail-closed：解析失败/版本不符一律 throw）→ `loadInstalled`
  （service.ts:866-917）无包裹 → C1 向量 2 → exit 1 → supervisor 退避重拉 ×5 →
  熔断全下线。手编坏一个 JSON 即锁死整个宿主，且无自愈路径。
- **修复方向**：readRegistry 损坏 warn+空档（坏文件转 `.corrupt`）；或
  loadInstalled 外层 catch 降级。
- **验证**：主线亲验（void-then 无 catch + readRegistry throw 路径）。

### C3 agent-loop 不向 llm.chat 透传 signal + 传输层无超时 → 中断失效 / 会话门永久挂死
- **位置**：`ac-agent-loop/src/service.ts:380-393`（step() 的 chat 入参缺
  `signal` 键——契约 `ac-llm/src/contract.ts:64-65` 已备好该字段、
  ac-openai-completions 已正确消费）；`ac-openai-completions/src/index.ts:111-125`
  （fetch 无任何超时）。
- **后果**：
  1. 用户中断/子代理超时只在**步边界**生效——当前步 LLM 请求继续跑完整轮
     （token 照扣、会话门不释放）；
  2. 网络半开/代理滴流 keep-alive：undici bodyTimeout 只覆盖完全静默，有心跳
     字节即无限续命 → run 永不收束 → 该会话**永久占门**，后续投递全部排队。
- **修复方向**：step() 补一行 `...(request.signal ? { signal: request.signal } : {})`；
  库层 `AbortSignal.any([callerSignal, AbortSignal.timeout(N)])` 兜底。
  附带修正：ac-conversation `NEXT_RUN_TIMEOUT_MS=190s` 注释称"对齐 LLM 180s
  超时兜底"——该 180s 兜底在 preview 并不存在（undici 缺省 ~300s），慢模型
  场景 next-run 消息会在 LLM 尚未超时前被丢弃。
- **验证**：主线亲验（step 入参无 signal + 全库无 LLM 超时）。

### C4 browser 守护进程三联缺陷：boot 无超时挂死 + FIFO 应答错位 + 失败当成功
- **位置**：`ac-web-tools/src/browser.ts`。
  - a) `:69-95` bootPromise 仅 resolve 永不 reject、无超时——daemon 起了但
    永不 ready（Playwright 首装/卡死）→ `send()` 永久 pending → run + 会话门
    永久挂死（loop 无工具级超时）；
  - b) `:116-120,139-146` 单命令 35s 超时后 FIFO `queue.shift()` 无序号——晚到
    应答 resolve 给**下一个请求**（A 的截图给 B），此后每次收发错位直到重启；
  - c) `:88-92` spawn 'error' 只记日志就 `done()`（resolve）——boot 失败当成功，
    下次 send 又 spawn 新进程，当次 send 对死 stdin 写（EPIPE）。
- **修复方向**：boot 加超时拒绝式收束；协议加 seq 或超时即 kill 重置；error
  路径 reject 并清 daemon。
- **验证**：主线亲验 browser.ts 全文。

## D. 治理与语义正确性（T0 / T0 边界）

### D1 yml 行熔断双重缺陷 → 核心行（含 plugin-registry 自身）可被持久熔断
- **位置**：`ac-plugin-registry/src/service.ts:546-594` + vendor
  `fiber.ts:147-154,575-595`。
- **双缺陷**：
  1. `fiberFailed` 用 `f.state === 'failed'` **字符串**比对——`FiberState` 是
     数字 const enum，永不相等（死代码）；唯一生效信号 `_error !== undefined`
     在依赖行 churn 的 UNLOADING/LOADING/FAILED 每次转换都计数 → 一次真实
     失败 + 一次依赖热更即 ≥3；
  2. `rowEntryIdOf` 沿祖先链找**最近** entry——动态插件 fiber 父=本行
     （README 明示），3 次 apply 失败的 Agent 自装插件（M23 常态迭代流）把
     **plugin-registry 行本身**推到熔断 → 动态插件全体卸载 + 急救 RPC 面消失；
     若错归属到 web-api/agent-loop 则主链路瘫痪。停用持久写 cordis.patch.yml。
- **修复方向**：计数判定改"本次转换 newState===FAILED（数字枚举）"；
  rowEntryIdOf 要求 fiber 恰为 entry 根 fiber，排除动态装载路径。
- **验证**：主线亲验（const enum 定义 + 字符串比对 + fiber 父链归属）。

### D2 boot 单行失败 = 整树回滚 + exit 1；78 协议从未接线；熔断对冷启动不可达
- **位置**：vendor `loader/src/config/group.ts:71-84`（allSettled 一败全抛）、
  `include/src/index.ts:273-289`；`ac-app/src/boot.ts:54-61`（顶层 await 无错误
  处置 → exit 1）；`ac-supervisor-core/src/index.ts:99-105`（78 分支全仓库无
  worker 发射点=死协议）；service.ts:547-572（行熔断计数对"每次进程死在
  第 1 次"的冷启动失败永不达 3）。
- **后果**：一行坏 → supervised 5 次无谓重拉后全下线；配置错被误报为 crash；
  自动降级（patch disable）从不发生。
- **修复方向**：boot.ts catch 装载拒绝 → exit 78（supervisor 已支持）。
- **验证**：主线亲验 boot.ts + 子代理验 vendor loader 链。

### D3 steer 收尾窗口吞消息——"已注入 ack"但本轮永不消费（T0 边界）
- **位置**：`ac-agent-loop/src/service.ts:263-264,337-358,205-207` +
  `ac-conversation/src/service.ts:298-322,472`。
- **时序**：run 自然收束判定后 → transform-run waterfall（异步边界）→
  after-run emit → run().finally 删 steerQueues——这段窗口内 conversation 的
  runs 门**尚未删除**（晚于 router.send 返回）→ deliver 走 steer 分支 →
  `steer()` 命中仍存在的队列返回 true → 消息入账+入视图+ack"已注入" →
  finally 连队列带消息删除，本轮永不读它。before-run veto 是同型第二窗口。
- **后果**：用户拿到 steered ack 后会话静默挂死至下一条外部输入（消息已持久
  化、下次 run 可见——可自愈故列边界）。群成员并发投递场景触发面更大。
- **修复方向**：run().finally 删除前检查 `queue.length>0` → 发
  `loop/steer-dropped` 事件，ac-conversation 订阅转 next-turn 重投。
- **验证**：主线独立推演时序成立（窗口=transform-run + after-run）。

### D4 waterfall `next()` 无重入守卫——双调 next = 剩余链+真实现整体重复执行（T0 边界）
- **位置**：vendor `events.ts:240-249`（`cbs.shift()` 无 once 包装）。
- **后果**：监听器双调 next（含 async 分支两路都调）→ `tool/before-execute`
  工具双执行、`plugin/before-load` 双装载、`loop/before-run` 双改写——框架
  零检测零告警；副作用不幂等处是数据级事故。M23 自开发插件人群无机械防线。
- **修复方向**：next 包装 once（二次调用 warn + no-op）。
- **验证**：主线亲验 vendor waterfall 实现。

## 结构性根因（修复时应整类处理，非逐点打补丁）

1. **"emit 悬空 Promise + 无进程级兜底"是全仓系统性模式**（C1/C2 及多个 T1 的
   共同根因）：vendor emit 不隔离 + Node ≥15 默认崩溃 + 散布的 `void` 无
   catch。一处进程级兜底 + vendor 逐回调隔离 = 整类消灭。
2. **"owning service 自持写法"导致原子写纪律弱化复制**（B2/T1-11/12 的根因）：
   fsx 基建（tmp+rename+retry+串行队列）就在 ac-plugin-core，但 config/singles/
   credentials/audit/shelves 各自手写弱化版。应统一走 fsx 或抽取共享写模块。
3. **测试面三类盲区**：崩溃注入（断电/半写/进程中途死）、并发窗口（compact×
   append、steer×收尾、双 connect）、敌意输入（构造器链、反斜杠、Origin）——
   804 条全绿恰说明现有测试全在单线程快乐路径上。
4. **治理面与 vendor 并发模型的接缝缺不变量**（D1/D2/T1-9 的根因）：熔断计数
   归属、配置回滚完整性、seam 守卫对称性——"治理工具自身把活系统搞死"是
   本轨道特有的一类风险，值得为熔断/清扫/热通道补一组"治理操作永不降低
   可用性"的元测试。
