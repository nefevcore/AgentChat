# CR 工具 v2 设计（cr-981）

> 定位不变：**本地零依赖脚本**（`scripts/cr.mjs`，Node 内置模块 only）+ **单文件 markdown 事实源**（`cr-log.md`）。
> 本文档是 v2 演进的裁决档案：范围、格式、状态机、追溯机制、守门不变量与非目标。
> 规约背景见 `epoch-marking-convention.md`（cr-1 起制度建立）；语义澄清：**CR = Change Record（变更记录）**，登记是自律动作，非 Change Request 审批流。

## 一、动机（现状数据，2026-11-10 实测）

- 985 条 / 325KB，44 个活跃日 → ~22 条/天；条目均长 190 字，>300 字 117 条（最长 1480 字）——规约「一句话」已失守。
- 最近 500 commit 中 345 个引用 cr-N——CR 已是事实变更主键，但链路单向、人肉、无校验。
- 目录区物理乱序 13 处；并行会话 append 无原子性（cr-24 跳号、cr-38 勘误漏排空洞两起事故同源）。
- 隐式状态散落文字（「待实施」「cr-8 方案落地于 cr-11」），欠账不可查。

## 二、结构化数据（要点 1）

### 条目语法扩展（向后兼容）

```
- 【cr-982 2026-11-10 一句话描述】{status|#scope…|→ref…}
```

- 尾部元数据块 `{...}` 为可选管道段，字段三类：
  - **status**：`plan` / `doing` / `done` / `drop`（词表见 §三）；缺省 = `done`（登记随批闭环的常态；跨会话 WIP 显式 `doing`/`plan`——尾部块只在非缺省或有标签/引用时出现）。
  - **#scope**：0..n 个标签，词表开放（建议沿用 conventional 域名：`#session` `#webui` `#mobile` `#docs`…+ 类型 `#fix` `#feat`）。
  - **→cr-N**：显式引用（依赖/落地/勘误关系），0..n 个。
- **存量 985 条不回填**：无尾部块一律视为 `{done}`——零迁移成本，语法双态并存。
- 描述内的 `docs/xxx.md` 路径沿用现状（无标记），由校验器扫描（§五）。

### 体量软门

- `append` 描述 >200 字打印警告（不阻断）：「细节应迁 docs/design/ 或 CHANGELOG，条目保持一句话」。
- 新登记默认鼓励按会话粒度合并（规约既允许，写入端纪律）。

## 三、状态管理（要点 2）

状态机（单向为主，最小集）：

```
plan ──→ doing ──→ done
  └──────────────→ drop      （任何态可弃置，须留一行缘由）
```

- `append` 缺省登记即 `doing`（动手前登记的既有仪式）；立项类显式 `--status plan`。
- `set <crN> <status>` 子命令就地改写尾部块（原子写，§四）；`done` 可选附 commit sha（由 sync 自动补，§四）。
- 查询：`grep --status plan` 列欠账清单——「登记了没落地」从此可查。
- 裁决：不引入 review/approved 态——单开发者 + agent 并行会话场景无审批面；不记录验证阶梯执行情况（提交前自查六问承担，防台账变流程负担）。

## 四、可追溯（要点 3）

三条链路全部落为**生成投影 + 校验**，不增加人工登记步骤：

1. **CR ↔ commit（反向索引）**：`cr.mjs sync` 扫 `git log` 全量 message 中的 cr-N 引用 → 生成 `cr-commits.json`（cr 号 → sha 列表 + 日期；**生成物禁手改**，同 row-catalog 纪律）；同时校验 message 引用的 cr-N 必须存在于目录——断链 fail-loud。
2. **CR ↔ 设计文档**：校验器扫描条目描述中 `docs/**/*.md` 形态路径，存在性检查（改名断链即红）。
3. **CR ↔ CR**：`→cr-N` 引用目标存在性检查；`grep --id cr-N` 精确取条（含被引处反查）。

`sync` 不自动运行——守门测试与 `stats` 前置调用（懒同步：投影缺失或过期时先重建）。

**增量化（随 v2 落地，非大量级后补）**：投影记录已扫到的 HEAD sha，下次只扫 `HEAD..记录点` 新增 commit；全量重建仅首跑与显式 `--rebuild`。git 面任何量级下都是常量时间。

## 五、守门不变量扩展（补充要点）

守门载体现状：cr-40 曾建 `src/ac-app/tests/cr-log.test.ts` 双锁（头行同步 / 无重复号），**src→packages 布局迁移后该测试已在树中绝迹**（现存唯一门 = `cr.mjs` append 内置不变量自检）。v2 守门重建为 `cr.mjs check` 子命令（零依赖、可直接本地跑 + 可被 CI/test 脚本调用），六条不变量：

1. 头行当前号 = 全卷最大号（既有）。
2. 目录区无重复号（既有）。
3. **目录区按号单调递增**（物理乱序即红——现存 13 处逆序须先理卷）。
4. 尾部块语法合法（status 词表 / #词法 / →目标存在）。
5. 条目内 docs 路径存在（**劝告锁**：三级回退链 原位 → docs/design → docs/design/archive，未命中软提示不红——登记先于写文档，硬校验会挡正常流程；实锤先例 cr-964 登记了从未提交的路径）。
6. commit 引用面（经 sync 投影）：message 中 cr-N 均存在。

### append 原子化（补充要点）

- 锁文件（`cr-log.lock`，O_EXCL 创建，stale TTL 10s）+ **写前重读、写后重验**；锁冲突时重读一次再试——并行会话跳号事故（cr-24）的结构性根因消除。
- **尾部 O(1) 追加写**：新条目在文件尾 append（头行同步仅替换该行字节段），免全文件重写——活动卷任意体量下 append 恒 <1ms，也减少 git 面每次提交的行变更噪声。
- EOL 守门保留（裸 LF 拒绝）；**cr-981 附记（已收口 cr-1000）**：工作区文件曾被 git `eol=lf` 再物化为全 LF 触发守门拒绝——根因 = cr-log CRLF 约定与 `.gitattributes` eol=lf 两个事实源顶牛。cr-1000 行尾统一后约定形态迁 LF，张力消解；混杂仍拒绝，全 CRLF 单态（旧约定形态）提示一次修形 LF。

## 六、分卷归档（补充要点）

- 阈值：主文件条目 >1000 时首切；此后每 500 条一卷。
- 形态：`cr-log.md` 永远 = 头部规约 +「当前号」+ 当前卷；旧卷移 `docs/design/cr-archive/cr-0001-0500.md` 等（同库同规约）。
- `grep` / 校验 / sync 全部跨卷；头行守门改为「全卷最大号」。
- 目的：读侧成本（人/agent 直接读文件）与并行会话冲突面，非性能（325KB 全文件解析毫秒级）。

## 七、CLI 面（v2 全量）

```
node scripts/cr.mjs append '描述' [--status plan] [--date YYYY-MM-DD]   登记（软门+锁）
node scripts/cr.mjs set <crN> <status>                                  状态流转
node scripts/cr.mjs grep <词>... [-n N] [--oneline] [--status S] [--id cr-N] [--scope #x]
node scripts/cr.mjs sync                                                重建 cr-commits.json + 引用校验
node scripts/cr.mjs stats                                               按日/状态/scope 计数 + 欠账清单
```

## 八、非目标（红线）

- 不服务化 / 不数据库 / 不网页看板——单文件 markdown + git 历史即制度价值。
- **`cr-N` 键永不改**（全仓 6400+ 引用、895 文件、345/500 commit；改名 = 丢 blame 断代，零功能收益）。
- 不做审批流（CR 语义 = Change Record）。
- 不做 CI 强制门禁（仓库既定：CI 无 lint 门禁，守门走本地测试）。

## 九、迁移计划（分批，各一批一 CR）

| 批 | 内容 | 破坏面 |

## 十、量级预案（10k / 100k 条）

实测外推（本条目 ~190 字，2026-11-10 基准机）：

| 维度 | 1k（现状） | 10k | 100k | 结论 |
|---|---|---|---|---|
| 全量解析 | 0.3ms | 3.3ms（1.8MB） | 34ms（18MB） | 任何量级都无压力 |
| append 重写 | <1ms | 12ms | 110ms | 分卷后活动卷恒 0.2MB，永远 <1ms |
| git blame（热文件） | 快 | 变慢 | 痛点 | 分卷根治：归档卷静态化后 blame 稳定，活动卷恒小 |
| sync（git log 扫描） | <1s | 数秒 | 数十秒+（>10 万 commit 输出数百 MB） | **第一个需要算法升级的点** |
| 读侧（人/agent 通读） | 可读 | 勉强 | 死亡 | 分卷后读活动卷；检索面全面走工具 |

裁决：
- **≤10k：零改动**——sync 增量化、append 尾部追加写、归档卷静态化（blame 减压）均已随 v2 各批落地，10k 量级直接受益。
- **10k~100k：唯一余项**是 JSON/TSV 索引投影转正为检索主面（grep 先查索引）；sync 与 blame 面已随 v2 收口。
- **100k+：技术上仍不必换载体**（归档卷静态、活动卷恒小），但届时按实际使用面重新评估——触发条件是真实负载，不提前。
- 语义面：10k+ 后台账作为「可通读时间线」已死，唯一接口是查询（grep/stats/索引）——条目粒度纪律（一句话）在大量级下价值放大而非缩小。

## 十一、开放问题

- 存量超长条目（117 条 >300 字）是否引导拆迁 docs——暂缓，新条目软门先行，存量随触碰顺手精简。
- `stats` 是否进 SKILL.md 日常例程——待实测查询频率再定（最少抽象）。
- archive 卷是否压缩进 tag——随发版流程评估。
