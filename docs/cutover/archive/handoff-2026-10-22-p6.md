## 3. 下一轮优先：前端流式输出问题

用户报告：前端消息**不流式**（疑似整段一次性出现或根本不出）。链路与既有证据：

- **数据链已验**：e2e-stream（真壳 mock run → tapAgent → broadcast → 真 WS 客户端收 `llm/delta-batch/delta-end` 帧形对拍）绿；cr-578 的 run-error 同管线两轮活体实证。宿主侧发帧大概率没坏。
- **嫌疑集中在浏览器侧**（preview 装配组合面，主线组件 × preview wire）：
  1. `rpc-wire.ts`（preview/apps/ui/client/）事件帧直转——主线 wire.ts 平移版，检查帧类型转发是否全（`llm/delta-batch` 是 rpc/event 帧还是旁带？）；
  2. 前端消费链 `feed-core.ts` / `useStream`（主线 ac-client-ui-conversation）：delta 到达后是否被 conversationId/agentId 过滤掉（stream-bridge 发的 meta 路由键：agent/conversationId/stepId/runId/sender/source——若前端按会话键对拍而 preview 会话键词形不同即静默丢帧）；
  3. wire 惰性连接时序（cr-535 曾有「无会话态 feed 未启动则不建立连接」的坑——流式帧可能在订阅建立前发出即丢，B3 旁带断连即丢语义）。
- **诊断路径建议**：CDP 打开 3830 → 会话发消息 → `page.on('websocket')` 抓 WS 帧看 `llm/delta-batch` 是否到达浏览器；到达 → 查前端过滤；不到达 → 查 tapAgent/桥接（宿主侧 e2e 已绿，重点看 rpc-wire 订阅时序）。
- 复现注意：产品宿主真 LLM 跑一问即可；诊断宿主（3851 + `--mock-provider 1`）毫秒收束，流窗口极窄——mock 流可用 e2e-stream 的慢 provider 桩形态。
