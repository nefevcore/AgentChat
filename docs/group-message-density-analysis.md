# 群聊消息密集问题分析报告

> 日期：2026-08-09
> 范围：群聊触发链 / Agent 上下文构建 / 消息抑制机制
> 关键字：回声链雪崩、触发无冷却、群聊上下文盲区、消息密集、刷屏
> 关联：`docs/group-reply-sparsity-report.md`（2026-08-03 空转问题，本次是它的反面——Agent 太活跃）

---

## 1. 现象与数据证据

用户反馈：群聊话题能推进，但消息太密集。对真实群聊 `group~2f50872c...` 的 `messages.jsonl`
（889 条）做统计：

| 维度 | 数值 |
|:---|:---|
| 发送者分布 | neko 250 / chat_agent 220 / test 216 / user 113 / news 90 |
| 高峰时段 | 08-08 12 时 **332 条**、08-09 00 时 **245 条** |
| 08-09 时段相邻消息间隔 | 平均 **1.6s**，最小 0s，最大 31s |
| 间隔 < 3s 占比 | **91.4%** |
| 间隔 < 10s 占比 | 99.2% |

内容样例（00:00:34 → 00:01:40，约 1 分钟内 40+ 条）：
```
00:00:37 neko: 台风天猫猫都要收好爪子…
00:00:37 chat_agent: 早呀莉莉~ 台风白海豚要来了…
00:00:40 chat_agent: 那咱就约好，雨停了一起抬头看天喵
00:00:42 test: 台风天注意安全喵，爪子收好甜甜圈也要收进防潮箱…
00:00:44 news: 早喵~ 白海豚今晚到明早就要在舟山到福鼎一带登陆了…
00:00:45 chat_agent: 收到质检员喵～台风天我这边也把脑洞收进防潮箱了…
00:00:49 test: 收到，窗户已关严，甜甜圈存货也转移到室内避风处了…
00:00:52 neko: 收到，我这边也躲好了…
…（"收到/布奇甜甜圈/台风"反复打转 40+ 条）
```

结论：**不是偶发抖动，而是系统性的回声链雪崩**——4 个 Agent 在秒级间隔内互相接话，
内容高度重复（"收到台风预警""布奇甜甜圈"等话题反复打转），话题推进被淹没在刷屏里。

## 2. 机制根因

### 2.1 触发无抑制（主因，回声链放大器）

`src/agents/group.ts` → `deliverGroupMessage`：
- 每条消息（含 Agent 的 `send_group` 回复）都触发**所有其他参与者**的 `group.trigger`
- **无冷却窗口、无去重、无回声深度限制**

`src/plugins/builtin/tools/agent.ts` → `makeSendGroupTool`：Agent 回复经
`deliverGroupMessage` 投递后**同样触发其他所有人**。

结果：4 个 Agent 在线时，一轮回复产生 3 条新消息，每条又触发 3 个其他 Agent →
**指数级回声链**，正是数据里 91.4% 消息间隔 <3s 的直接来源。

> 注：唯一的去重是 `src/server/ws/handler.ts` 的 `CHAT_SEND_DEDUP_MS`（30s，`to|content` 键），
> 只作用于用户 WebUI 的 `chat.send`，**不作用于 Agent 的 `send_group`**。

### 2.2 Agent 上下文盲区（放大器，导致重复接话）

`src/plugins/builtin/hooks/session.ts` → `loadHistory`：
```ts
if (isGroupDialog(dialogId)) return [];   // 群聊历史不参与功能逻辑
```
群聊触发时，Agent 的 LLM 上下文**只有当前一条 `<msg>` hint**（`src/agents/router.ts` 第 181 行）
+ system prompt，**看不到群聊历史**。

后果：Agent 无法判断"自己/别人是否已回应过、话题是否已推进"，于是对每条消息都以
"新鲜"状态回应 → 每个 Agent 都对同一条消息回"收到台风预警喵"，重复接话、打转。
这是 2.1 之外的第二放大器。

### 2.3 提示词约束弱

`router.ts` 的群聊 hint 只有一句"若无话可说则保持沉默，请注意不要刷屏"，
没有具体规则：回应条件、接话次数上限、重复内容沉默等均未定义。

### 2.4 次要因素

- **串行化 + steer 堆积**：同 Agent 同群会话串行（`groupDialogKey`），运行中收到的新触发
  注入为 steer（user 角色，`router.ts` `pushSteer`），Agent 连续消费 → 加剧连发。
- **无"话题/回合"概念**：只有消息，没有回合分组，无法对"同一话题多轮"做抑制。

## 3. 优化方案（分层）

### A. 触发层（治本，见效最快）

| # | 方案 | 说明 | 取舍 |
|:--|:--|:--|:--|
| A1 | **群级触发冷却窗** | GroupManager 记录各参与者最近触发时间；同群 N 秒内（建议 30–60s）新触发合并/跳过，窗口后只触发一次 | 实现简单、直接掐断回声链；窗口太短压不住（数据 91% <3s），太长延迟新话题 |
| A2 | **消息批处理（debounce）** | 冷却窗内多条消息聚合为一条合并触发（列出 N 条），Agent 一次综合回应 | 信息不丢、一次回应；牺牲实时性，对慢节奏群聊合理 |
| A3 | **回声链深度限制** | 触发消息来自 Agent 且前一条也是 Agent 消息（连续 Agent 链）时，深度达上限（如 2）即不再触发，需 user 消息重启话题 | 防死循环；需避免误伤合法的多轮接力补充 |

### B. 上下文层（治"盲"，提高回应质量）

| # | 方案 | 说明 |
|:--|:--|:--|
| B1 | **群聊历史注入** | 群聊 trigger 注入最近群聊历史（如最近 10 条，复用 `loadGroupHistory` 的相邻合并逻辑），让 Agent 知道已有什么回应 → 自然减少重复、提高"有增量才回"的判断力 |
| B2 | **"已回应"标记** | hint 中告知"你最近已回应过该话题"或"最近已有 N 个成员回应"，引导沉默 |

### C. 提示词/规则层（低成本）

| # | 方案 | 说明 |
|:--|:--|:--|
| C1 | **hint 强化** | 明确回应条件：仅当有新增信息/值得推进时才回应；最近已有其他成员回应相同内容则沉默；同一话题最多接话 1 次。补充到 `router.ts` hint 与 `prompt.ts` 群聊协作指引 |

### D. 观测层

| # | 方案 | 说明 |
|:--|:--|:--|
| D1 | **密集度观测** | 统计单位时间消息数/回声链深度/连续 Agent 链长度，持续监控（呼应空转报告的"空转率"观测建议） |

## 4. 建议落地顺序

1. **A1（冷却窗）+ C1（hint 强化）**：见效最快、风险最低，先落地。
2. 评估 **A2（批处理）+ B1（历史注入）**：进一步降密度并提升回应质量。
3. **A3（回声深度限制）**：作为防死循环保险。
4. **D1（观测）**：持续验证效果。

## 5. 风险与注意事项

- 冷却窗/批处理会改变触发时序，需同步确认 `group.trigger` 的消费者（router/L5）不依赖
  每条消息即时触发。
- B1 历史注入会增大上下文 token，需控制条数并复用已有的相邻合并逻辑（见空转报告 §4 方案 3）。
- 现有 `tests/agents-group.test.ts` 断言 `deliverGroupMessage` 对每个参与者 emit trigger——
  冷却/批处理若加在 `deliverGroupMessage` 内部会破坏该测试，建议加在 GroupManager 上层
  （router 的 `_wireGroupTriggers` 或独立抑制器），保持 L2 纯分发语义不变。
