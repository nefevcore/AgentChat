## 遗留疑点 e2e 确定性复现（§八/10 终判）

| 实验 | 结果 |
|---|---|
| ① reload 后正常发送（9+9） | ✓ 回复「18。」上屏 + 落账（触发正常 compaction：1754 行 → archive history_1.jsonl.gz + 160 行主文件） |
| ② **restart_host + 页面不刷新 + 发消息（6+7）** | ✗ **确定性复现**：busySend 跨重启卡死（stopping 态常驻）、点「发送」走 `interruptGeneration()` 分支（onPrimary 忙态语义）、消息不落账、看门狗不自愈（30s+ 无反馈） |
| ③ reload 后重发（6+7） | ✓ 立即恢复：「13。」上屏 + 落账 |

**定性：宿主重启后页面链路断裂且不自愈**——两层断点：

1. **页面侧**：cr-948 epoch 换代通知未触发页面 reload（pageAge 跨宿主重启持续增长实证）
   → 页面 WS 疑似死连不重连、stale busySend 永驻（发送按钮永久变「停止」）；
2. **宿主侧**：dispatch 拉壳成功但信封未达壳——designer 壳 22:45:26 被 dispatch 触发拉起、
   boot.ready 完成（pid 45536 存活 25 分钟），但正本/inbox/journal 零写入、零 run。
   **cr-1297「taps 重建唯一触发面 = onAdopted」推断不成立**。

修复方向（另批立项，不属本渲染管线计划）：页面 epoch 检测链失效定位（onEpoch 是否注册/
WS onclose 是否触发）+ 宿主 dispatch→tap 信封丢失环节定位。

## 结论修正（cr-1303 事后复核）

**实验②被 contextBusy 串台缺陷污染，不能作为「宿主重启断链」的证据**：执行实验时本会话（Agent 自己的 run）必然在跑 → 页面 `contextBusy` 恒真 → 点「发送」实际走 `interruptGeneration()`，消息从未进入发送链。「消息不落账/无回复」由此被充分解释。

仍待复测项：宿主重启后 designer 壳被 dispatch 拉起（boot.ready 完成）但正本零写入——该现象**不依赖页面**，需在排除串台后重做 e2e 才能定性（§八/10 已同步降级）。正常链路结论（①③）不受影响。
