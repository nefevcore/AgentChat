# cr-1075 修 cr-1074 引入的包内循环依赖 + 补 manifest.name 冒充校验

## 动机（cr-1074 自查）

1. **包内运行时环**：`plugin-guard.ts` 为取 IMPORTED_ROWS 而 `import { IMPORTED_ROWS } from './index.ts'`——而 index.ts 导出 plugin-dev.ts、plugin-dev.ts 导入 plugin-guard.ts，成 index → plugin-dev → plugin-guard → index 环。check:deps R5（运行时环）只查包间边，不查包内文件环，故阶梯未拦。
2. **守卫有洞**：cr-1074 只校验**模块名**（`mod.name`），但钉死目标是 `manifest.name`——manifest 叫 `ac-evil` 的插件（NAME_RE 允许）钉死后 fiber 名即 `ac-evil`，照样骗过门行 `trusted()` 的 ac- 前缀判定。装得进、守得住名、照样直通——cr-1073 定级的向量只堵了一半。

## 改动

- **去环**：plugin-guard.ts 不再 import 包索引，改用前缀规则（`ac-` / `shell-` / `root`）。覆盖面经全仓核实：93 个官方能力包 `export const name` 全是 `ac-*`；壳内工厂行（make\*Row）全是 `shell-*`；`logger-console` 行无名（继承祖先）且经 IMPORTED_ROWS 装配，不过本闸。
- **单源化**：命名空间规则落 `ac-plugin-core/src/manifest.ts`——`RESERVED_PLUGIN_NAME_PREFIXES` / `RESERVED_PLUGIN_NAMES` / `isReservedPluginName()`，两个消费面共用一份：① `validatePluginManifest`（安装期早失败，用户当场见可诊断错误）② 壳 `plugin-guard`（装载期硬闸，防 manifest 事后被改/绕过安装器）。单向依赖 ac-shell-rows → ac-plugin-core，无环。
- **补洞**：`guardPluginModule` 同时校验 manifestName 与模块名，任一冒充即拒载（此前只查模块名）。
- 测试：plugin-guard 7 例（新增 manifest.name 冒充两例）+ plugin-core 集成补命名空间保留 4 断言；installer 测试夹具改名 `ac-plugin-demo` → `demo-plugin`、`ac-plugin-bad-engines` → `bad-engines-plugin`（原夹具名本身违反新规约，属夹具过期）。

## 裁决

- **前缀（ac- / shell-）而非全名单**：名单会随新增包漂移（漏登 = 洞），前缀是官方包的既有命名事实（全仓 93/93 核实），且不引入包索引依赖。
- **安装期 + 装载期双检**：单点校验不够——manifest.json 在已装目录里可被事后改写（壳侧 hash 复验另有一层），装载期硬闸是信任面的最后一道；安装期校验负责体验（早失败 + 教改名）。
