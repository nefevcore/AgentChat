# cr-1182 上下文注入改造：datetime 落盘 + 系统事件日志 + 环境脉搏注入

日期：2026-11-21 · 状态：doing

## 动机

两个用户报告的问题：
1. **datetime 注入不落盘**——两形态（singles 信封 splice / 其余会话 DATETIME 段）都只活在单次 run：system prompt 从不落盘、信封改写无 recordContext，回放历史无时间锚。
2. **持久化 Agent 无环境感知**——timer 唤醒的 Agent 不知道宿主重启过、行集变了、壳换代了——对账困惑的根源。

## 用户裁决（2026-11-21）

1. datetime 全形态统一 per-run 落盘日期 context 行；新增间隔阈值（≥1h，基准 = agent 最后回复时刻，非用户发送）注入时间信息行（日期+时刻+「距上次回复已过 X」）；**移除 DATETIME 段**。
2. 系统事件清单可注册扩展，当前最小集：host-boot / shell-start / rowset-changed（timer-changed 裁决不进——per-agent 作用域与全局公告流错配，正位是 timer 域状态）。
3. 注入时机：会话被唤起时（loop/before-run）。
4. 归属：纯库 + 宿主单写者挂点 + 壳侧注入行（跨进程共享走数据根文件）。

### 批2：ac-datetime 改造

- loop/before-run：per-run recordContext 落日期锚（source='datetime'；日内幂等 = 私有状态 .day-anchor.json per-会话判重——信封回放是 wrapper 包裹形态，扫描判重不可靠）
- 间隔注入：loop/after-run 记录最后回复时刻（files/<agentId>/datetime/.last-reply.json，error/interrupted 不刷新）；before-run 比对 ≥1h 注入 timeInfoLine（user 行追加）
- 周几计算修正：Intl weekday 直取（原 UTC 构造近似法在非整日时区边界错位）

### 批3：ac-env-pulse（新壳行）
- loop/before-run 读事件 delta → 有增量时 [系统状态] 行注入（recordContext 落账 + wrapSystemReminder 同字节 user 行双写——ac-memory cr-1102 模式）
- 水位 files/<agentId>/env-pulse/.anchors.json（per-agent×会话；0 是合法水位——首注空日志场景）
- 首注只初始化水位不注历史（历史事件无「自上次活跃后」语义）

### 装配归位

## 运行时验证与缺陷修补（宿主重启后）

**已验证生效**（news 壳 09:30 档 timer run，账本实证）：
- `{"type":"inject","content":"[当前时间] 2026-11-21 周六","injectSource":"datetime","label":"日期锚"}`——日期锚落账、回放可见
- 状态文件 `files/news/datetime/{.day-anchor.json,.last-reply.json}` + `files/news/env-pulse/.anchors.json` 就位
- `meta/system-events.jsonl` 7 条（host-boot + 6 shell-start）

**缺陷发现与修补**：shell-start 是 per-agent 事实（nana 的壳拉起与 news 无关），
但 env-pulse 不按 agent 过滤——每个 Agent 会看到全员壳拉起噪声。修补（数据面
作用域词汇，非特判）：
- `SystemEvent.agentId?`：有 = per-agent 事件（读侧按 viewer 过滤）；无 = 全局公告
- `appendSystemEvent(root, kind, payload?, agentId?)`；orchestrator 挂点传归属
- `filterEventsFor(events, viewer?)` + `renderSystemEvents(events, viewer?)`
- env-pulse 注入传本 Agent；delta 全被过滤时水位照推进（防每次 run 重扫）
- shell-start 渲染句改为「你的 Agent 壳重启（新代 pid X，进程内会话状态已重置）」——
  per-agent 过滤后语义自明，无需内部 id

验证：三包 30/30；typecheck / lint / check:deps 全绿；全量 pnpm test **3413/3413**（458 文件）。

## 已知遗留

- **首注基线**：env-pulse 首注只初始化水位（不注历史事件）——存量 Agent 首次跑新代码时会错过重启前的最后一轮事件。这是设计取舍（历史事件无「自上次活跃后」语义），非缺陷。
- **旧会话日期锚回补**：既有会话历史无日期锚（改造前不落盘），不回溯补齐——新 run 起自然有锚。

## 第二处缺陷：存量行读侧兼容（壳重启后自查发现）

**现象**：修补前那一代代码已往 `meta/system-events.jsonl` 写了 7 条 `shell-start`，
agentId 落在 `payload` 里（无归属位）。修补后的读侧只看顶层归属位 → 这批旧行
全部降级为「全局公告」→ 每个 Agent 都会读到**别人**的壳重启。

**修法**（读旧写新兼容窗，数据根契约既有纪律；append-only 日志不改历史行）：
读侧解析时 `payload.agentId` 提升为归属位 `agentId`。旧行因此同样按 per-agent
过滤。另修 `shell-start` 渲染句——pid 缺席（存量行）时不输出 `pid ?` 占位噪声。

**真实数据验证**（workspace/home 7 条旧行）：
- news 视角 → host-boot（全局）+ 自己的壳重启
- tester 视角 → host-boot + 自己的壳重启（看不到 news 的）
- 旁观者视角 → 只有 host-boot，无任何壳重启

验证：三包 31/31；typecheck 绿。
全量 `pnpm test`：457/458 文件（唯一失败 = ac-host-rows/singles-row「cr-1100 快照分居
sweep」——并发 flaky，单跑 32/32 全绿；该文件属他人在途改动，min 修改时刻 9:16:36
早于本变更所有全量跑且前三次全绿）。

## 第三处缺陷：respawn 形态漏记事件（壳重启后实测发现）

**现象**：第二次 restart_shell 兑现后，事件日志仍停在 7 条——本次壳换代
**没落 shell-start**。查因：挂点在 `ensureAgent` 的 spawn 成功后（orchestrator
L254），但 `restart_shell`（exit 42）/ 崩溃重拉走的是 warden 内部 respawn 链
（supervise.ts 的重拉循环），根本不经过 ensureAgent → 最需要知情的那类事件
静默丢失。

**修法**：挂点改到 `handle.onAdopted`（supervise L226 每次 adoption 触发——
首拉 / warden respawn / restart 全形态覆盖），配两段式（已 adopted 的补记一次，
回调只对未来生效）——与既有 re-tap 接线同款模式，不双记。

**锁定测试**：`apps/host/tests/orchestrator-events.test.ts`（新增 2 例）——
首拉落一条且归属位正确；模拟 exit 42 → warden respawn → 断言事件数 ≥2
（该用例在旧挂点下必红，是本次缺陷的回归防护）。

验证：apps/host 120/120；typecheck / lint 绿。

## 第四处缺陷：接管活壳误报为「壳重启」（本会话收到注入后自查发现）

**现象**：宿主重启后，本会话**真的收到了**注入：
`[系统状态] … - 09:51 你的 Agent 壳重启（进程内会话状态已重置）`——
但我的壳**根本没重启过**（保壳保 run：restart_host 不杀壳）。

查因：`adoptLiveShells`（cr-967 换代接管）走 `adopter` 的 socket-only 分支
（`adoptSocketShell`，无 spawn），但同样触发 adopted 回调 → 我的钩子把它记成
`shell-start`。sequence 实证：seq 13 `__creator__` 出现在 host-boot 后 18ms，
典型接管时刻；且 5 个 agent 同批出现 = 接管清单，不是 5 个壳同时自重启。

**危害等级高于前两处**：漏记只是「少知道」，误报是**假信息**——Agent 被告知
进程内状态已重置，会重做在途工作 / 重复执行已完成步骤。

**修法**：`takeoverAdoption` 标记集——adopter 接管路径打标，取证钩子消费后
即清（只影响该次 adoption）。接管 ≠ 壳重启，语义边界明确。

**锁定测试**：`apps/host/tests/orchestrator-takeover-events.test.ts`——
adoptLiveShells 接管成功（句柄入池）但 **shell-start 事件数 = 0**。

验证：apps/host 121/121；我的改动文件 lint 全绿（apps/host 另有 4 处既有
lint 欠账在未改动的 e2e 测试文件里，与本变更无关）。

## 收尾

- restart_host ×2（第一次让事件挂点生效、第二次让接管修正生效）
- restart_shell ×2（作用域过滤 / 读侧兼容提升）
- 四处缺陷全部由运行时实物发现——测试全绿 ≠ 运行时正确
