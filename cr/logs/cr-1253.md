# cr-1253 记忆 seq 撞号防线（cr-1252 补修）

## 现场（运行时验证发现，非测试可预期）
cr-1252 壳重启后核验现网 14 个 Agent 顺编结果：全部头注释带 seq、零重复。唯 tester 有 3 条头注释无 seq（时间戳 23:45:43——换代窗口）。根因不是顺编失败，而是 **tester 自己的壳仍在跑旧代码**（我的壳重启不连带它），继续用旧 mintEntry 写无 seq 条目。

## 缺陷
`nextSeqOf` 只取物化 maxSeq（tester=227），而 3 条无 seq 条目经 parse 位置派生 seq=228-230 ⇒ 新代码壳下次 write 铸 228，**与已存在的 #228 撞号**。cr-1252 设计时假设「无 seq 行经位置派生进入 seq 空间、下次铸造自然跨过」——该假设不成立：位置派生值恰好落在 (物化max, 条目数] 区间，必须显式把条目总数纳入下界。

## 修法
1. `nextSeqOf` 三维下界：`max(maxSeq(主文件), 条目数, forget 高水位) + 1`。
2. 顺编保号：`materializeSeq` 保留已物化 seq（跨会话引用不失效），无 seq 条目从 `max(已物化)+1` 起分配并跳过已占用号（集合式分配，乱序输入也零撞号；forget 空号不复用）。
3. **`MemoryEntry.materialized` 标记**（core 层）：parse 侧唯一可靠地区分「物化 seq」与「位置派生兜底」——此前 `isMaterialized` 守卫（forget 工具）与顺编保号都因用 `at + seq>0` 判定而误认无 seq 头为已物化。

## 验证

## 残余
tester 壳在换代前仍写无 seq 条目（其自身壳生命周期决定，非本包可控）——撞号已由条目数下界兜住；其壳换代时 boot 顺编会把存量无 seq 条目接续物化。
