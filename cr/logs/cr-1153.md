## 根因诊断（供修复批参考）

1. `packages/ac-ledger/src/service.ts:532` recordsFor 排序 `(a.seq ?? MAX_SAFE_INTEGER)` 把**无 seq 的 legacy 行排到尾部**（即被消费方当作最新）。cr-974 行级 seq 持久化后，无 seq 旧行整批跳到尾部，插入序≈时间序的隐含前提失效。
2. `packages/ac-memory/src/index.ts:130-145` 倒扫取最后命中行做锚 → 命中几十天前的 legacy 行（tester S=33 / admin S=74 / news S=100）；两者皆缺时回落 `S = 0`（fail-open，与注释声称的 fail-closed 相反）。实测复现：tester~user 按 S=33 算出的 delta 条数 = 84，与观测注入头「新增记忆 84 条」逐字吻合。
3. `packages/ac-ledger/src/writer.ts:41-64/160-176` `tailMaxSeq` 只读文件末 32KB 且逐行 JSON.parse；memory 单行可达 35KB~140KB → 窗口内几乎无可解析行。实测 tester~user 真实 max seq=850，tailMaxSeq 只取到 79 → 新 writer 从 3 起分配，seq 不再单调（10:43~10:48 写入的行 seq=107/3/4/5）。
4. `recordsFor` 的 inject 事件投影不带时间戳（只有 seq），消费方无时间可排序。

附带：`renderDelta` 无 token 预算（只有 renderSnapshot 接 maxTokens）——重复注入因此把 140KB 级别内容灌进每轮上下文。
