# cr-1163 restart_shell 退出与 boot「已重启」注入竞态根修

## 动机（现场：会话 01a1f2f1，2026-11-20 09:38）

双开会话场景，cr-1160/1162 重启密集工作流（4 次 restart_shell + 6 次 restart_host）下，前端出现持久红错 "This operation was aborted"（刷新仍在）。盘上账本 L1169-1170 实锤：`run-restarted-078ead9a` 起跑 30ms 即被中止，以 `finish=error` 落持久账本。

### 时序还原（全证据来自盘上）

1. 重启密集循环 → 每代壳 boot 都有「已重启」注入排队（gated on inboxRecovery——恢复面每封排队信是一个 3-7 分钟的 LLM run）。
2. gen B（09:22:16 boot）注入排了 16 分钟；期间本代自己的 restart 意图挂起（另一窗口 run 占着「全闲门」直到 09:34）。
3. 09:38:28 c1a7ac9d 收束：①restart-ready → 写 marker ③ → decideExit(42) 进入关闭序列；②恢复队列收净 → gen B 的陈旧注入此刻投出。
4. 09:38:30.8 注入 run 在正在关闭的壳里起跑 → 30ms 后被关闭序列（fiber 收割）abort → error 落账。

### 根因（结构性）

**注入是漂浮的 fire-and-forget 任务，与退出路径零协调**：
- 注入 gated on inboxRecovery（可能长达数分钟）；本代 restart 兑现（exit 42）不等「本代是否还有未兑现的 boot 注入」。
- 两者触发条件同源（队列收净）→ 必然同拍 → 注入落进关闭窗口。
- 陈旧注入不作废：gen B 注入 gen A 时代的 marker，兑现时 gen B 自己已在退出——纯多余且有害。
- 竞态中止落 error 行 → 前端持久假红错，与真实故障不可区分。

### 与既有工作的边界

- 双开不是根因（只是把 restart 推迟到恰好同拍）；单窗口同样竞态。
- 与 cr-1159（多键修复）正交：cr-1159 改通知的形状（单键→键集），本 CR 改注入的生命周期归属。

## 修复（结构：注入纳入退出协调）

注入从漂浮任务改为**带取消契约的本代在途工作**（`restartedNoteDelivery` 工厂，apps/shell/boot.ts）：

1. **take 契约**：`ShellBootResult.restartedNoteTake()` ——退出路径同步调用，取走全部未投键；投递循环见 pending 空 → 停止（无关闭窗起跑点）。
2. **通知恰好一次**：main 的 restart-ready 监听器先 `take()`，未投键并入本次重启 marker（下代投递）——通知跨代不丢不重。
3. **在途头排除**：restart-ready 在注入 run 收束点**同步发射**，此刻投递循环悬在 `await receive` 上、shift 未执行——take 若取走在途头即重复注入。`delivering` 标记 + `take` 排除之（在途 run 已收束，receive 只剩微任务收尾，必在本代完成）。

### 时序不变量（为何契约闭合无泄漏）

restart-ready 只在 activeRuns 全空时发出，而注入投递本身就是一个 run 注册在 activeRuns 上——take 时不可能有投递在途执行体（只有微任务收尾），未投键 = 必然还挂在恢复面队列里。契约闭合。

## 测试中的两次返工（值得记录）

1. 第一版「部分投递」用例假设 30ms 时 conv-b 未投——实际 receive 依次 await，push 先于 sleep。教训：异步时序断言要显式建模「在途」状态。
2. 修断言后暴露**真实语义缺口**：take 先于 shift 执行（restart-ready 同步发射窗）会把已投键取走 → 下代重复注入。修法即上述「在途头排除」——测试驱动出了正确语义。
