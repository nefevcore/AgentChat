# cr-1171 timer LLM 面补全（update / list 回显 / cancel 归档）

> 登记于 2026-11-20 · →cr-1164 →cr-1170 · 状态：done

## 动机（news 反馈三条）

1. **无 update 语义**：改条目只能 cancel + set——id 变、记账（firedCount/armedAt/lastSeq）清零、两次调用非原子。
2. **list 不回显 conversationId**：想知道实际投递目标只能读 entries/timer.json——"改完不读盘验证等于没验证"。
3. **cancel 不写归档**：撤掉的条目静默蒸发（timer-archive.json 只有迁移期 7 条 script-face-retired），留痕只能翻 audit.jsonl。

## 改动面

- **update（timers-row + face）**：幂等改写单条——按 entry_id 替换，行侧记账保留；face 层未传字段继承现值（只改 when/text/conversationId/enabled 不丢其余）；过 v2 参数闸 / 归属闸（cr-1170）/ 授权闸（cr-1166）同款防线。
- **list 回显（face）**：text 与 conversationId 平铺顶层（缺省时给派生值 owner~owner——投递目标一眼可见，不再需要读盘核对）；action 原样保留。
- **cancel 归档（timers-row cancelEntry + face）**：撤条走 completeEntry 同款归档链——status **'cancelled'**（归档状态随终结语义映射：until/expired/manual = completed、撤销 = cancelled、迁移丢弃 = dropped）、firedCount 固化、timer-archive.json 可查；face 优先归档版，行缺席回落旧 save 过滤（跨版本兼容）。
- **TimerArchiveRecord.status 联合扩 'cancelled'**。

## 裁决

- update 继承而非全量替换：改一个字段不该要求调用方回传整条——丢失字段的风险大于多写继承逻辑。
- cancel 归档复用 completeEntry 链而非新写归档路径：同一条链保证形状一致（archive 消费方无特判）。
- list 的 conversationId 缺省给派生值而非省略：投递目标【总在场】比【有时在】更可预期——news 的痛点是"不知道投去哪"，省略字段会重新引入这个疑问。
