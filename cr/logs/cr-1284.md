## 测量依据（本机数据根，2026-11-24）

- 典型 Agent 面 14.2–15.9 KB ≈ 4.3–4.8K tok（`boot-graph.json` × `tool-catalog.json`）。

- 压缩变体：creator 面 −27%（工具描述首句）/ −31%（+参数描述 80 字）/ −59%（删净参数描述）；程序化 SDK 块 −29%。

## 额外轮子的成本核算结论（同批补充）

- 单次 `tools_help` 往返 = 该步整份 prompt + 正文进历史后的重复付费；等于一个 run 全部 schema 收益的 5–66 倍（按 Agent 上下文规模）。
- 盈亏平衡调用率 `f*` = 1.5%（`news` 类长上下文）～22%（`__creator__` mean），中位约 6–10%；help 只能是偶发行为。
- 实证：103 111 条历史子调用里参数/schema 类失败仅 10 条（0.01%），失败主体是语义错（`edit` old_string 未命中 763、`pwsh` 命令失败 767）→ 真需求率远低于门槛，但「养成先查习惯」会立刻反超。
- 据此调整：主修复路径改「报错即文档」（校验错误内联参数表 + 摘要，零额外轮次），`tools_help` 退为主动深查补通道；help 落账标 `injectSource` 不进跨 run 重放；P6 以调用率 <5%/run 为否决线。

## ## 真 tool_search（动态工具面）结论

- 额外成本两项：搜索往返（≈该步整步 prompt）+ 前缀失效 `(M−1)·P̄·hit`（工具面在历史之前，改它等于整段历史重编码）。
- 实测解锁次数下界：每 run 不同工具数中位 3（p90 7，4486 个 run 统计）。
- 单次面增长成本 = 1.50M（`__creator__`）/ 3.45M（`news`）hit-token 当量 vs 每 run 全量面节省 130K / 53K → 11.5× / 65.6×；按 3 次增长 34.5× / 197×。
- 判据 `ΔS > P̄/N`：面 4–4.8K vs 摊薄步上下文 6.9K–102K，现行全部 Agent 不满足（`__creator__` 0.67 次往返/run 预算、`news` 0.04）。
- 摊销形态：逐步/每 run/每会话三档全亏（会话中位 2 run，855 会话中 573 个 ≤2 run）；仅「大面(ΔS>15K) + 冷边界一次定面」有区间。

## 除描述瘦身外的杠杆（实测）

- 面裁剪空间（从未调用的工具占面 schema 比例）：quant 92%、abap-dev 64%、admin 60%、impc 54%、neko 44%、creator 35%、news 21%、standard 2%。单位收益大于描述瘦身，但属 Agent 职责决策（行集），不进本档批次。
- 工具合并：SAP/ADT 32 个 `adt_*` ≈50 KB schema →「单工具 + action 枚举」可到 10 KB 级（数量级收益，中高风险）。
- 参数 schema 结构化简（每层 additionalProperties / 重复 type / anyOf 合并）：低风险 ~10%。
- provider 显式 cache 断点：本仓未打 `cache_control`（grep 零命中）；DeepSeek/OpenAI 自动前缀缓存下边际收益小。
- 天花板：schema 占稳态 prompt 0.4–1.0%、锚定 18–37%；更大降幅在历史（creator 工具结果：pwsh 45%、read 35%、grep 8%），属 compaction / 结果预算线。

## 「改后还能不能正确用工具」的可预测性（静态分析结论）

- 拆三层：① 选对工具 = 静态可测（全目录摘要近重复仅 restart_host/restart_shell 一对 0.47）；② 填对参数 = 按工具分级；③ 遵守纪律 = 只能实测。
- **必现 bug**：朴素「取首句」在 68 工具里产出 9 个破损摘要（未闭合括号/引号，如 glob 截在 `"**/*.`、read 截在 `output: { pa`）→ deriveSummary 必须在括号内安全断句。
- 参数描述依赖度三档：A 安全 37 个（4 280 chars）、B 分级 27 个（11 861 chars，单位/格式密集）、C 高危 4 个（browser 16/19 参数带 action 前缀、subagent 12/13、goal 5/6、adt_create_destination 30 参数）→ C 档参数描述不得截断。
- 真实验路径只有 BFCL 两臂（`pnpm bench --model --base-url`），分开看「选择准确率 / 参数匹配率」；mock 模式是脚本回放，不能验证模型行为。两臂全跑约 3–4M prompt token 量级。

## per-tool `help` 参数成本面（补充）

- 相对全局 tools_help 的唯一结构优势：收益（省 schema）所有请求享受，成本（一次往返）只在用到该工具时付——收益/成本相关。
- 前提修正：browser 一半体积是结构（19 参数 344 tok）移不走；描述最重的是 adt_create_destination（86% 可移）、subagent（85%）、browser（62%）。
- 单项开销：30 tok/工具。全量注入 20 工具 +579 tok（吃掉 44% 摘要收益）；按「文档重」判据（参数描述≥120tok 或参数数≥10）只命中 18/68，creator/standard 面仅 browser+subagent = +60 tok，净省 ≈1 058 tok/请求。
- 分 Agent 盈亏：standard 1.7×、creator 1.3×、tester 5.7× 可做；news 0.5% 门槛 vs 9.0% 使用率 = 亏 18×；writer 亏 2× → 必须按面开关。
- 实现：投影期注入 help 属性 + `ToolsService.execute` 入口拦截（不调 execute）+ `validateInvoke` 豁免 required；**必须拦在 waterfall 之前**（browser 是 needPermission，否则会弹审批卡）。一处拦截即覆盖 MCP 等第三方工具。
