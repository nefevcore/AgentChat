# cr-1255 activation 锁 pid 复用致永久锁死

## 现场与根因

Windows pid 复用激进（writer 实测 12h 内即可复用）：壳崩溃不跑 exit handler
→ 锁文件残留（设计内——靠接管方清理）→ 无关进程占用旧 pid → 新壳 boot 时
isAlive(旧pid) 恒真 → 永远 refused，陈锁接管机制被废，Agent 永久无法启动。

根因：pid 存活被当作持有者存活的单证。pid 只能证明「这个 pid 上有个进程」，
证明不了「是当年持锁的那个壳」——pid 复用后判活面整体失效。

## 修法（结构性：接管权威与诊断分离）

接管权威 = 任一证死因子（lock.ts judgeHolder）：
1. pid 已死（内核裁决，不可骗）
2. 心跳租约超限：锁 mtime 超过 LOCK_DEADLINE_MS（4×30s）未刷新——pid 复用
   现场真壳死后无人 touch，租约必然超限，此类问题整类关死；锁文件创建即
   起租（O_EXCL 的 mtime），心跳自锁获取即 touch（覆盖装配窗——装配中的壳
   不会被误判死）

诊断定谳（不授权接管）：refused 时 manage 探针（probeActivationHolder）connect
transportHint 发 { ctrl: 'probe' } 帧核对 bootId——应答匹配 = 真活壳（错误消息
附凭据）；无应答 = 近期崩溃的租约残温（≤4 周期，重试即接管）。探针不授权
接管的裁决：装配窗口的真壳尚无 socket，探针无应答 ≠ 死——授权即双壳
split-brain。

## 附录：admin 的独立诊断与验证记录（2026-11-23）

### 发现经过与影响面

writer 自 11-22 20:39 起 **12 小时无法启动且无人知晓**。触发暴露的是 08:36 一次记忆整理通知：
发消息 → 宿主 ensureAgent 拉起 → 壳 boot 失败，才在日志里看到原因。
**若无这次通知，它会一直躺着。**

批量扫描 12 个 Agent 的 activation.lock（比对 pid 指向的进程名）：

```
__creator__   pid=27804 -> (dead)      pid 未被复用，正常可接管
其余 10 个     -> 进程名均为 AgentChat  正常持有
writer        pid=20892 -> svchost    *** PID 复用 ***
```

11 正常 / 1 中招。但这是概率事件，任何 Agent 壳崩溃后只要 pid 被复用且恰好有人发消息，即复刻同一剧本。

### 实测证据链细节

```
activation.lock：{"pid":20892,"bootId":"5b3588bf-...","acquiredAt":"2026-11-22T12:37:23.501Z"}
                mtime = 11-22 20:39:24（此后从未更新）

Get-Process -Id 20892            => 存在，ProcessName = svchost   ← 复用
node -e "process.kill(20892,0)"  => EPERM
```

pid 存活判定的 Windows 实测对照：

| pid | process.kill | Get-Process |
|---|---|---|
| 20892 | EPERM | 存在（svchost） |
| 99999999 | ESRCH | 不存在 |
| 4 | EPERM | 存在（System） |

EPERM 在「pid 指向真实存在的其他进程」时必然成立，而 pid 复用恰恰制造这种情形。
旧 `isAlive` 的 `catch → code === 'EPERM'` 是 POSIX 语义（进程在但无权限），在 Windows 上
对无关进程同样成立 ⇒ **死壳的锁被无关系统进程「继承」，永不接管**。

### 自愈靠运气，不是修复（关键教训）

writer 最终在 08:41:26 站起来了，但**不是修复**：

```
08:36:45 boot 失败
08:37:49 boot 失败
08:38:54 boot 失败
08:41:26 boot 成功  ← 因为 svchost(20892) 恰好在此时退出
```

实测确认：`Get-Process -Id 20892` 现已不存在、`process.kill` 返回 ESRCH。

这使缺陷**更危险而非更轻**：
1. **可能永久锁死**——svchost 类长期驻留服务可能永不退出。
2. **会被误判成偶发抖动**——「重试几次就好了」是最坏形态，没人会去追根因。
3. **暴露依赖外部唤醒**——死锁 12 小时无人知。

### 排查判据（沉淀）

> **Agent「不响应」时，第一步查 `agents/<id>/activation.lock` 的 pid 指向什么进程。**
>
> 若显示 svchost / System / 其他非 AgentChat 进程，即确诊 pid 复用锁死。
> 此时「锁被进程 20892 持有」里的 20892 是个**无关系统进程**，不是僵尸 AgentChat
> —— 按后者排查会跑偏（我曾据此怀疑「有残留壳进程」）。

辅助信号：锁 mtime 长期不动（> 数分钟）而 pid 存活 ⇒ pid 复用强提示；
真活壳会持续 touch（30s 节拍）。

### 独立复刻验证（代码层直调，绕开 gate 与沙箱）

构造 writer 现场（pid 指向活着的非 AgentChat 进程 + 锁 mtime 陈旧），直调 `acquireActivationLock`：

```
A  复用 pid(4/System) + 租约过期(1h) => acquired  ✓
   证据：心跳租约超限（mtime 2026-11-23T00:55:26.260Z，阈值 …）
B  复用 pid + 租约新鲜              => refused   ✓（真活壳不抢）
```

旧实现在 A 场景返回 `refused` —— **这正是 writer 被锁死 12 小时的判定**。
新实现与 pid 假活彻底解耦，判定只落在租约上。

装载与测试：lock.ts mtime 09:47:53 < 宿主 boot 09:52:27（pid 37564）✓；
envelope-core 81 例全绿。

运行时心跳实测（admin 壳，30s 节拍严格推进，非仅代码存在）：

```
09:48:00.441 -> 09:48:30.453 -> 09:49:00.454 -> 09:49:30.462
```

### 同族归纳（本类缺陷的通用形态）

与 ISSUE-25（排程挂在会被重载的行 fiber 上）、ISSUE-30（[timers] 日志 0 条落地）同族：

> 进程存活 / pid 存活 / 锁文件存在 / 日志无错误 —— 这些都**不是「功能正常」的充分证据**。
> 每一条「看起来在」的信号，都要配一个独立的功能面判据。

本例的具体表现：**把「锁的存在性」与「持有者的存活」当成了同一件事**。

### 残余（admin 补充）

- 旧代壳（boot < 09:47:53）无心跳、无新判死逻辑。它们不会误判（锁里是自己真实 pid），
  风险仅在「旧壳崩溃 + pid 被复用」时出现，随 idle-exit 换代自然消失，无需强行重启。
