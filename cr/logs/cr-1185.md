# cr-1185 名册脱离 runs/snapshot：session-index roster 小表 + 帧驱动定向入账

> 登记 2026-11-21 · →cr-1142（roster 预览权威化——本 CR 把权威源从 snapshot 内嵌升级为独立单源面，并填掉 cr-1142 遗留的惰性陷阱）/ →cr-1138（sessionMeta 聚合面——roster 表是其列表化延伸）

## 一、动机

名册（agents/groups lastActivity/lastMessage）此前从 runs/snapshot 聚合（fetchAgents/fetchGroups 搭矩阵便车）：

1. **载荷耦合**：名册首屏拉全量 snapshot（conversations 数组 + running + groups），snapshot 展开可能触发展开盘读（memo 失效时）——名册首屏被最慢链拖住；
2. **cr-1142 惰性陷阱**：last 身份/时标取 sessionMeta(refresh:false)，未入账会话返回 null 回落旧形态（replay 任意末行——run-end/step 事件行常占位 = 漂移）；
3. **存量死键**：fetchGroups 以 gid 匹配 conversations[].conversationId，而群 gid 无账本目录（真实数据根只有 g-<gid>~<member> 成员流）——群 lastActivity 的 snapshot 合成恒 undefined，实际只有本地 WS bump 在动。

## 二、设计（独立小表——IM thread 表形态）

- **ac-session-index roster 表**：每会话一行（conv 主键）——发言口径 last_speech_ms/last_agent/last_role + last_text（末发言行指针 seek 回源取正文截 120 字符——**内容不驻索引**，指针索引本色）+ 活动口径 last_at_ms + speech/total + stat 复合指纹（fp_size/fp_mtime）。
- **同源维护**：refreshConversation 尾部 recomputeRoster（records SQL 聚合 + 末发言行 seek）——索引可重建语义不变（纯缓存）。
- **群行折叠**：gid 无账本目录，rosterSnapshot 读面把成员流行（g-<gid>~<member>，sessionKindOf 判 group）折叠进 gid 键（last_* 取时标最大、speech/total 求和）——群 lastActivity 从此来自真实成员账本。
- **新鲜度三通道**：① 帧驱动定向入账（host-web tap 桥：run/settled + 独立私信入站——setImmediate 出帧路径、同拍微批、索引行缺席跳过〔cr-1142 高频面禁隐式建索引裁决保持〕）；② boot 预热 + 60s reconcile 挂 warmRoster（rosterGaps = stat 指纹对账——缺口增量填充 + session/roster-warmed 广播）；③ RPC warm:true 前端自补。
- **conv 归一**：settledConvOf（与 unreadAxisKeyOf 判据单源同构但不筛 viewer 参与——名册要全部会话新鲜度；agent⇄agent/自会话同样入账）。
- **RPC session/roster**：{rows, warm}——零盘读全表投影；索引行缺席 fail-loud（同 session/meta 姿态）。
- **前端**：fetchAgents/fetchGroups 改消费 session/roster（rosterToTails 投影进 toAgentList 既有合成管线——单实现）；chat-core 订 session/roster-warmed 帧重拉名册（冷启动 warm-up 补齐收口帧，零轮询）。

## 四、裁决记录

- **正文来源 = 独立小表 + 指针 seek**（用户裁决 2026-11-21：IM thread 表形态）：last_text 不做 records 行列（每行带 120B 只有末行被读——浪费），而是 roster 行重算时 seek 回源单行读。「零语义」红线实质保持（内容不驻索引、可全量重建）。
- **成员流折叠在读面**（rosterSnapshot）而非写面：写面折叠需群成员表依赖（groups-row 耦合进 session-index——破坏纯库边界）；读面正则折叠零依赖。
- **agent⇄agent 对桶不入名册**（现语义保持——矩阵视角承载）；但其 roster 行照常维护（矩阵/仪表未来可用）。

### 批3（同日追加：snapshot 展开面零盘读收口）

- **conversations[].last 退役**：消费方核验（源码 grep + mobile 打包产物）确认唯一消费 = runview 类型声明（投影不使用）——名册已脱离，尾部摘要在 snapshot 内无意义。

### 性能事故复盘与修复（同日三改：RPC 冻结 ~6s → 分片对账）

**症状**（用户 webui 控制台实录）：冷启动首批 RPC（interaction/list、agents/list、session/roster、system/version 等十余个方法）全部 ~5.8s 且同刻批量返回——不是单 RPC 慢，是**宿主事件循环被同步段冻结 ~5.8s**，全部并发 RPC 排队等解冻。

**根因**：批 1 引入的 `rosterGaps()` 是**全量同步 stat 扫**（1334 会话 × readdir + 3×stat + SQLite 读），单次 ~1s 无让出。触发面：① `session/roster` RPC 的 `warm:true` 分支（首屏 fetchAgents/fetchGroups 各带一次）；② RPC 返回值里的 `warm` 热度字段又算一次；③ face-ops boot 预热链与首轮 reconcile 各一次——首屏窗口内叠加 ~6 次全量扫。测试未抓：测试数据仅 2-3 会话，同步段微秒级。既有 reconcile 全量扫不卡是因其有 12ms 时间片分片让出——rosterGaps 漏了同款纪律。

**修复**（结构对齐 reconcile 而非加缓存）：
- core：删全量 `rosterGaps` → `rosterGapOf(convId)` 单会话原子（stat 3× 微秒级）+ `allConversationIds` 枚举（零 stat）作分片数据源；注释明示「有意不做全量版」防回归。
- web-api：`session/roster` 删 warm 参数与热度字段——纯读小表（毫秒级、恒快）；冷填充归 warmRoster + `session/roster-warmed` 帧通知重拉。
- face-ops：warmRoster 重写为「枚举 → 逐会话 gap 判定 → 缺口 refresh」12ms 分片循环（SLICE_MS 同款纪律）；in-flight 串行化防 boot 预热与首轮 reconcile 同拍双跑。
- 前端：fetchAgents/fetchGroups 去 warm 参数。

**教训**（入个人方法论）：面向宿主单线程的读面，任何「全量 + stat」组合都必须默认分片让出——除非能证明规模上界（如测试 3 会话）；RPC 路径只做 O(1)/O(已索引) 读，全量对账一律后台分片。测试规模不足以暴露同步段时，用真实规模数据根做一次运行时验证再收口。
