# cr-1246 ac-config 跨进程热同步（目录 fs.watch → 防抖 reload）

## 症状

宿主 WebUI 写盘（config/set、config/save → ctx.config.set/merge 原子落盘）后，
在跑的壳进程读不到新配置：`ConfigService` 构造时读一次 config.json，内存态
只经本进程 set/merge/reload 刷新；`reload()` 全仓生产零调用（仅测试）——
「外部改文件后的同步入口」从未接线。壳内 llm-pool 等行订阅 `config/changed`
热更（撤/挂 diff），但壳内该事件此前无 emit 源（宿主 emit 不跨进程）。

## 根因

配置热更链路只完成了**单进程**语义（写 → 事件 → 订阅刷新），漏了**跨进程**
半边：宿主-壳双进程各自实例化 config 行、共享同一 config.json，但没有机制
把「盘变了」翻译回「本进程 reload」。

## 修复

`ConfigService` 构造挂目录 fs.watch（`ctx.effect` 随 fiber 回收，
ac-session-index 同款先例）：事件防抖 100ms 后调 `reload()`。零新事件、零新
RPC——选盘 watch 而非消息通道：writeJsonAtomic 的 rename 原子性天然触发
目录 watch（watchLedger / watchAsksOf 仓内既定形态），无宿主-壳广播依赖。

- 自身写盘回声：`reload()` 深等价判等（cr-377）即静默——零自激（有测试锁定）。
- 外部写盘：reload 吸收 + `config/changed` 广播（载荷 = changedKeys 顶层 diff）。
- `persistent:false` 不阻 idle-exit 收割；watcher error 自关；目录缺席静默。
- events.ts `@scope host` 不动——变更语义不变，壳内订阅方按既定契约刷新。

## 改动面

- `packages/ac-config/src/service.ts`：构造挂 watch + `watchFile()` 私有方法 + 头注。
- `packages/ac-config/src/events.ts`：注释补跨进程吸收记载（签名零变化）。

## 观测点（本轮补充）

跨进程热更原先**零痕迹**：失效时无从诊断（本轮活体验证即卡在此处）。补两处：

- watch 挂载失败（目录缺席/EMFILE 等）→ `[config] 配置 watch 未挂上（路径）：原因` warn；
- 外部写盘实际热载（reload 换引用）→ `[config] 外部写盘热载：<file>` info。
  自身 set/merge 回声不打印（深等价保持原引用）——日志只记跨进程来源。

## 运行时验证（活体）

1. 真实目录机制探针（`sandbox/watch-probe-cr1246.mjs`）：目录 watch + 临时文件
   rename 覆盖 → 5 个事件（rename/change 混合）——机制在 Windows 真实目录成立。
2. 跨进程写盘探针（`sandbox/probe-cr1246.mjs add|remove`）：向主数据根
   config.json 注入 `llmProviders.__probe1246 = {}`（缺 base_url → 永不被注册为
   provider，纯观测用）。壳内 llm-pool 收到热更应 warn「缺 base_url」。
3. 生产 config.json 已先备份 `sandbox/config-backup-cr1246.json`，验证后恢复原状
   （remove 后与备份语义一致、1256 字节、零残留）。

**活体结果（两侧）**：

- **宿主侧**：新宿主（pid 41812，19:38:12 装载含观测点代码）在外部原子写盘后打印
  `[config] 外部写盘热载：…/config.json`——目录 watch → 防抖 reload 链路在真实
  生产进程中成立。
- **壳侧**：独立进程装生产同款行（`sandbox/shell-side-verify-cr1246.mjs`，
  `ctx.plugin(configRow, { root })` = 壳内装配形态），外部进程（另一 pid）原子写盘 →
  读值翻新 `a=2` / `addedByOther=yes`、既有键 `keep` 不受影响、`config/changed` 精确
  广播 1 次且载荷 `["a","addedByOther"]` = `changedKeys` diff。PASS。

两证据合起来覆盖了完整指控面：壳进程（非写盘方）能读到宿主/其他进程写入的新配置，
无需重启。壳内 root 契约（`rowOptionsFor` → `config: { root: dataRoot }`）与宿主同源，
故生产壳换代后行为一致。

### 观测面事实（壳 logger 不落盘——既有架构，非本改动引入）

曾计划在 `shell-<agent>.log` 里看壳侧热载日志，实测该文件只含 boot 编排行
（`[shell]` / `[host.orchestrator]` 前缀），cordis logger 行（`[I]/[W]` 格式）数量为 0：
壳进程 stdout 由 `orchestrate.ts` 以 pipe 消费（行流仅排水/诊断转发，不落盘），
只有 **stderr** 经 `hooks.onStderrLine` 落盘。壳 logger 走 `console.log` = stdout，
因此生产壳内的 `ctx.logger.*` 输出不可从盘上观测。

影响与处置：本条改动本身无需依赖该日志（壳侧证据已由「独立进程 + 生产同款装配 + 跨进程
写盘」取得）；该观测缺口是平台既有问题，不在本次改动面内，不擅自扩大修改——记为观察项。
本轮生产壳上的跨进程写盘仍做过实际动作（注入后恢复），配置无损（校验 = 备份、零残留）。

**「生产壳装的是新代码」的时序证据**：`service.ts` mtime = 19:37:55，壳 pid 18720 启动
= 19:49:53、宿主 pid 41812 启动 = 19:38:12——两进程启动均晚于最后改码（Node 直读
源码、无构建缓存），故装载的必是含 watch 与观测点的新代码。

## 生效

ac-config 两树各计（host.yml + shell.yml 都点名）——restart_host + restart_shell
后运行时生效。
