# cr-1254 记忆整理轮 dream 机制

## 动机
长期记忆时间线只增不减：现网 14 个 Agent 中 news 535 条/428KB、designer 338 条，快照注入预算（缺省 2000 token）仅覆盖最近 10-15 条——旧条目常态沉底，只能靠 grep 翻；重复、过时、被推翻的结论与有效教训混在一起，稀释检索质量。memory-timeline-plan §3.7 早已预留「整理（sleep-time，二期）」，cr-1252/1253 的写口（物化 seq + memory_forget）是其前置件。

## 依据（外部调研）
Anthropic《The components of agent memory》（2026-11-05）Dreaming 范式：空闲期对照转录复盘——纠错（Pokémon 实测：错记忆未纠正卡关三次，纠正后通关）、构建表征（wiki 跨 128 轮 13%→48%）、层级晋升（顶层必须小，dream 大量工作在「保持顶层小」）、目标塑形；**给方向不给硬规则**（强模型上「只记失败」规则反而损失大半记忆增益）。Letta sleep-time compute：后台子 Agent 巩固记忆不打扰主工作，触发按完成步数或压缩时点。Stanford Generative Agents：记忆流 + 重要性 + 周期性 reflection。

## 归位裁决
实现在 `ac-memory` 行内（`packages/ac-memory/src/dream.ts` + 构造尾挂载），**不新开行**：整理对象是记忆时间线本身，离开记忆服务整行无意义（inject 判据）；独立开关走 `settings['memory'].dream.enabled`（缺省开）。避免新增行/菜单脚手架（无需 shell.yml 版本戳与 row-catalog 重生成）。

## 形态
- **触发**：`loop/after-run` 检测——间隔（缺省 20h，含 ±15% per-Agent 哈希抖动防惊群）∧（新增 ≥ 8 条 ∨ 条目 ≥ 400 硬阈）；同一 Agent 单飞（pending，15min TTL 自愈）。
- **唤醒**：`conversation.deliver` 普通 run，自会话 `agent~agent`（不打扰用户线程），`mechanism: true` / `budget: 3` / `maxSteps: 20` / `meta.origin='dream'` / `requestId=dream-run-<ts>`。
- **收束**：整理 run 的 after-run（runId 前缀 `run-dream-run-`）→ 写水位 `.dream.json`（lastDreamAt / lastEntryCount，tmp+rename 原子），不做轮询等待；前缀检查同时保证不自激。
- **写口**：整理轮用 Agent 自己的 `memory_grep` / `memory_write` / `memory_forget`——产物是「新条目 + 遗忘旧条目」，不直接改写文件（append-only 与回收站语义不被绕过）。
- **降级**：conversation 行缺席 → 静默不整理；无记忆 → 跳过；投递失败 → 清 pending 不记水位。
- **指令**：四类动作（纠错/合并/沉降/精炼）+ 纪律（不凭空新增、本次 ≤20 条操作、机制任务不发起对话），做多少由 Agent 判断；统计行给出条数/时间跨度/tag 分布，避免为摸底翻全量。

## 与归档整理轮的分工
归档（ac-shell-rows/archive.ts）读**会话转录**产摘要 → token 治理（上下文窗口）；dream 读**记忆时间线**产整理 → 知识治理（跨会话长期可用性）。二者共享「机制信封唤醒普通 run」范式，写口与对象不同。

## 验证
ac-memory 50/50（+6 dream 用例：唤醒形态/新增不足不唤醒/硬阈绕开新增门槛/自身收束记水位且不自激/settings 关闭/conversation 缺席静默降级）；typecheck 绿；定向 lint 绿；全量 unit 与 integration 见收口记录。

## 自审修正（实施中）
① **重试下界**：投递成功但 run 迟迟不收束时，pending TTL 到期会反复重投——加 `lastAttemptAt`（1h 重试下界，落盘与 pending 互为兜底）。
② **readState 字段白名单缺陷**：初版逐字段白名单回读，把新增的 `lastAttemptAt` 静默剥掉 → 重试下界形同虚设。改为原样返回（只挡非对象畸形值），新增字段不再失传；用例改为「预置 lastAttemptAt → 不投递」的真测试（原用例被 pending 抢先拦住，未覆盖该路径）。
③ **per-Agent 抖动**：间隔 ±15% 哈希抖动，防多 Agent 同批部署的惊群。
④ **类参数属性触犯 strip-only 红线**：`constructor(private ctx: Context, ...)` 在 tsc 与单测下无感，但 Node 原生 TS 加载器直载报 `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX` → 所有 spawn 真壳的 e2e（apps/host、ac-host-webui）成片超时「壳就绪超时（锁未出现）」。改为显式字段声明 + 构造赋值。**教训**：仓规「不用类参数属性」的检测面目前只有 e2e（代价高、易被当成环境抖动）——建议后续加一条静态扫描（packages/*/src 里 `constructor(private|public|readonly …)` / `enum` / `namespace`）。

## 运行时观察（2026-11-23 00:05，壳重启后）
- 全 Agent 无 `.dream.json`、无 `[dream]` 日志、无 `timeline.forget.md`——**符合预期但暴露结构性边界**：本机制的触发挂在 `loop/after-run`（run 收束后检测），而壳层实行 idle-exit 收割——**完全闲置的 Agent 壳不在进程，永不触发**。
- 现网定时任务分布：7 个 Agent 有周期任务（news `every 30m`、neko `every 7h30m`、多个 daily）→ 每天自然唤醒，dream 正常触发；6 个无周期任务（abap-dev / deloitte-consultant / designer / impc-consultant / writer / user）仅在用户消息时唤醒。
- **语义上可接受**：闲置 = 无新记忆 = 无需整理。唯一漏的是「条目数超硬阈」维度（如 designer 338 条已逼近 400，长期无人问津则不会自动整理）。
- **真实数据端到端实证**（沙箱根 + 生产 admin 时间线 244 条）：emit `loop/after-run` → 立即投递 dream run（自会话 `admin~admin`、`mechanism:true`、`maxSteps:20`、`requestId:dream-run-*`）→ `.dream.json` 落 `lastAttemptAt` → 模拟整理轮收束 → 落 `lastDreamAt/lastEntryCount:244` → 再检测不重复投递（冷却生效）。取证：全部断言成立，链路在生产规模下打通。
- 演进位（未实施，需裁决）：对齐既有 `archive-all` 机制任务范式加一条 `dream-all`（host 侧 timers-row dispatch 分支 + ac-timer-core task 白名单 + 壳侧 boot.ts 消费 mechTask + ac-memory 暴露强制整理口），由一条全局定时任务驱动，兜住长期闲置 Agent 的膨胀治理。

## 已知边界（一期显式接受）
- **触发依赖 run 收束**（见上节运行时观察）：无周期任务的闲置 Agent 不会自动整理。
- 纠错材料目前只有记忆条目自身（对照会话转录纠错 = 二期：需给整理轮一条读归档段的通路，现行 Agent fs 域不含 `agents/<id>/sessions/`）。
- 不做 wiki/索引表征（Anthropic 的高阶形态）；一期只做条目级整理。
- 整理轮本身耗 token：一次 ≤20 步、20h 一次、按 Agent 抖动错峰。
