## 关键裁决

- 逻辑压缩（compaction 单事件，纯追加）与物理回收（compact 重写）解耦——压缩可高频、回收低频；
- 双维边界 (boundarySeq, endTs) + 文件位置兜底——僵尸行在谓词层根治；
- 概要提交协议（形态校验）——review 终稿元文本不再冒充摘要；
- session-index 增 generation/tokens 面——三口径（注入/阈值/仪表）单源收敛。

## 追问裁决（2026-11-20 同日）

「压缩轮定义为 single 会话（纯回顾/分析）」否决：读面需求 ≠ 存储位置需求。补 §2.8 四层读面（数据 compactionFactsOf / 展示 TokenGauge 压缩历史区 / 深查归档段+run 轨迹 / 问询即席注入）；§4 不做表增列。否决四由：双事实源或跨桶依赖、singles 生命周期错配（递归压缩）、名册污染（cr-1100 教训）、机制日志归位是 a~a 自会话。

### 运行时验证与口径修正（重启后实证）

宿主重启 + 新 schema 建立后，用生产数据复算发现并修正一处口径缺陷：

| 会话 | 索引口径（修正前） | 索引口径（修正后） | 真实 API prompt | 结论 |
|---|---|---|---|---|
| news~news（a~a 自会话，0 压缩代） | 2,091,557 | 701,653 | 767,206 | 修正后差 65K = system+tools ✓ 同源 |
| news~user（3 压缩代） | 活跃代 3,396 | 3396（不变） | 144,216 | 差 140K = system+tools+摘要头（前端 displayTotal 补）✓ |

**缺陷**：`estimateRowTokens` 对 `step/tool-call-result` 未过滤 `subcall: true` 行——run_code 程序内子调用结果（news~news 现场 1.7M token）被计入，而 `ac-archive-core/replayTokensOf` 明确跳过（不进回放注入）。后果：阈值误判（2.09M vs 701K）+ 仪表高估 3 倍——正是本 CR 要根治的 C5「三口径分叉」的新形态。

**修正**：① `estimateRowTokens` 补 `row.subcall === true → 0`（与 replayTokensOf 逐字同源）；② 新增 `EST_TOKENS_VERSION` + `meta` 表口径版本对账——版本不符或无标记但有账面行 → 整库弃重建（估算语义演进的自动失效，不迁数据不猜旧值）；③ 回归用例锁定（4KB subcall 结果 → 活跃代 < 300）。

**第二处缺陷（架构级）**：B3 把阈值检测改成「软取 ctx.get('sessionIndex') 直读索引」
——但 session-index 住**宿主**进程（host.yml）、archive 行住**壳**进程（shell.yml），
壳侧 `ctx.get('sessionIndex', false)` 恒 undefined，该分支是死代码（实施期实证）。
修正：删跨进程软取，改壳内分代估算 `estimateOf(uuid, { activeOnly: true })`——用
ac-ledger 的 `rowShadowedBy` 纯函数（两进程共享判据、不共享实例）+ 按 run 末事实
seq/ts 判伪行（与 foldLlmReplay orphan slot 同源）。语义与宿主侧 activeContextTokens
一致，符合「能力间不传引用」红线。用例⑤锁定（压缩后活跃代未超阈 → 零新压缩代）。

**第三处缺陷（旧三连面）**：`compaction/start` 与 `compaction/summary` 行曾进 records
聚合（我只把单事件 `compaction` 加了白名单）——污染 sessionMeta.total 与 ts_num 活跃度；
且旧三连的摘要长度丢失（摘要住 summary 行、代在 end 行建）→ 压缩历史展示面对 admin~admin
这类老会话误标「概要未更新」。修正：compaction 事件族**一律**不入 records；summary 长度经
per-file pending map 在 end 建代时回填；rebuild 时同源清 compactions 表（否则重建重复建代）；
口径版本升 v2。用例锁定（三行不入聚合 + lastType 不被顶掉 + 摘要长度回填 + 重建幂等）。

**第四处缺陷（boundary ≤0，危害最大）**：存量老 writer 显式写 `boundarySeq: 0`
（admin~admin 现场 4 代全 0）——我在重写事件归并时把 cr-974 的回落写成 `?? 0`，
两处后果同时成立：① 壳侧 `estimateOf(activeOnly)` 的 `rowShadowedBy` 对 0 边界判
`seq ≤ 0` 恒假 → 已压缩内容全当活跃 → 老会话每 run 收束反复触发整理压缩（花钱且
账面不降）；② 宿主侧 `activeContextTokens` 取 MAX(generation) 那代恰是压缩后的空壳。
修正：**boundarySeq ≤ 0 视为无有效边界 → 回落 end 行自身 seq**（events-v2 与索引
`boundaryOf` 同判），口径版本 v3。离线副本实证 admin~admin：boundary 784/1086/1252/1418
（递增 4 代）、壳侧 activeOnly 保留 1/1419 行、LLM 回放 1 条——三面对齐。

**第五处缺陷（两半，仪表口径末梢）**：

① **同 RPC 内调用顺序**：`session/tokens` 先调 `activeContextTokens({refresh:false})`（高频面不建索引，
cr-1142 裁决）、后调 `compactionFactsOf`（内部 refresh）。首次访问索引未建 → 前者返 null →
回落全量盘读（含 shadowed）——正是要根治的 C5 分叉。修：**先 compactionFactsOf 建面、后读值**。

② **摘要头漏计**：`activeContextTokens` 只累 records 行 est_tokens，而回落路径 `estimateReplayTokens`
含 `opts.summary`。压缩后活跃代只剩 run-end 行时会显示 0%，但 LLM 上下文里有摘要 system 头。
修：compactions 表增 `summary_tokens`（入账时按摘要内容实算，CJK 0.6/ASCII 0.3），
activeContextTokens 加「最新可用摘要」token（跳过 summaryOmitted 代——与 foldSummaryOf 回落同判）。
离线实证 admin~admin：`summaryTokens` 575/661/670/639，`activeContextTokens` = **639**（此前 0 或 572774）。

**顺带纠错**：上一轮诊断报告的 news~news「134K 回放口径」是错的——v2 事件行无 `role` 字段，被那版 replayTokensOf 的 v1 谓词漏算；真实 prompt 为 767K。v2 会话的步级体积由 fold 的 step/* 折叠承担。
