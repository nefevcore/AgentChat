# cr-1119 机制通知排队落账时序修复

- 性质：fix（→cr-1099 restart_host 完成通知的第二轮活体暴露；cr-971 消费点落账原则对 queue 路径的补齐）
- 日期：2026-11-16

## 现场（01a1dff7 会话 messages.jsonl 尾部）

seq 1164/1165 restart_host 回执（00:20:23.27）→ **seq 1166 机制 context 行落盘（00:20:28.51，早于原 run 收束 9s）** → seq 1167-1169 原跑 run 终稿（00:20:37.1）→ seq 1170 原跑 run-end → seq 1171-1173 通知触发的续跑轮。行序 = 通知在前、原终稿在后；通知正文却声称「run 已自然收束，其终稿都在上下文中」——落盘时刻为假；链跑轮（deepseek-flash）见序恰好颠倒，回复"等宿主重启完成通知后即可做运行时确认"，不识自己就是被通知唤醒的轮。

## 根因

壳侧 receiveEnvelope 对 busy+next-turn 排队信**收信即落账**（L312 deliverRow），而 run 层链跑消费（runSettled→takeFromInbox）等原 run 收束后才开轮——run 时序对、账本时序错。cr-971 为 steer 路径立了「受理不落账、消费点落账、文件序=模型消息序」原则，注释却写「run/queue 路径不受影响」；cr-1099 现场修正二给通知信加 lane:'next-turn' 修的是 busy-steer 抢素材问题，没动落账时序。机制行（payload.mechanism，cr-946）= 轮边界语义，消费点落账才对齐文件序与真实轮序。

## 修复（packages/ac-shell-conversation/src/service.ts）

1. receiveEnvelope：plan=queue 且 mechanism=true 时不再收信落账（mechQueued 门）。
2. 新增 deliverQueuedMechRow：消费点按 requestId 判重（hasInboundRow）补落机制行。
3. 链跑消费点（runSettled→takeFromInbox 得信后）与 drainQueuedTurn（reviewRun 收束唤醒）调用补落。

用户排队行维持到达序落账（链跑交接测试 L885/L915 锚定的产品语义）；steerQueued 无需动（cr-971 journal 路径已覆盖）；壳死于排队窗口 → 下代 boot 恢复面 recovered 重投（信封在 inbox durable），run 路径照常落账——补行门收敛。
