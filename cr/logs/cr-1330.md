# cr-1330 dual-view P4a 修复：群成员下钻链路 + 可发现性

> 2026-11-26 · dual-view-session-plan P4a 的实地走查修复（用户反馈「前端没看到成员轨迹下拉」）。

## 一、背景

P4a（cr-1328）交付了群成员轨迹下钻（`ConversationHeader` 的成员下拉 → `openPairView(gid, member)` → pair 只读视角），
但单测与构建全绿，**用户实际看不到/点不动**。实地走查诊断出两个真实缺陷 + 一个观感缺陷。

## 二、根因与修复

| # | 缺陷 | 根因 | 修复 |
|---|---|---|---|
| 1 | 选中成员后主区掉成「选择一个 Agent 开始对话」空态 | 模板表达式 `@change="openMemberTrace(($event.target as HTMLSelectElement).value); ..."` —— **Vue 模板表达式里的 TS `as` 断言**在编译产物中未能正确取值，`member` 恒为空串 → `openPairView(gid, '')` → pair props `b=''` → `isPair=false` → dialogId 落空 → 空态 | 模板只写 `@change="openMemberTrace"`；取值与占位复位移到 script（`ev.target.value`） |
| 2 | 下钻标题裸露内部 gid | pair 视角 `endpointOf(a)` 走 `roster.getAgentName(id) \|\| id`，gid 不在名册 → 回显 `g-mthfaf3e-tmx1 × Neko` | `ui.pairView` 增可选 `label`（第三参随带群名）+ header `epA` 消费（label 在场替代 id）；`openPairView(a, b, label?)` |
| 3 | 可发现性差（用户「没看到」） | 原生 `<select>` 无视觉权重，且**只在群会话渲染**（1v1 无此控件，符合设计但易误解） | 胶囊样式 + `成员轨迹 ▾` 文案 + hover 主色高亮 + `Tooltip` 说明 |

## 三、附带发现（机制层，非本批修复）

**`build:channel` 后宿主 channel revision 清单不自动刷新**：浏览器继续加载旧 revision 的通道 bundle（实测 `ui-runview/94637054077cb733` vs 产物 `3ee31452c74ea9c6`），
新代码「构建了但不生效」，且无报错——极易误判为代码 bug（本轮排查耗时主要在此）。
restart_host 后 revision 一致。已记入设计文档 §六；后续可考虑 revision 热更新（build 后主动通知宿主重扫）。

## 四、验证

- typecheck / webui:typecheck / 定向 lint 全绿
- `ac-client-ui-conversation` + `ac-client-ui-runview` + `ac-client-ui-layout` 455 例绿
- 双构建配对（build:channel + webui:build）+ restart_host 刷新 revision
- **真机端到端实测**：群会话 → 下拉选成员 → pair 只读视角（`只读` 徽标 / 42 条消息 / 2 条轨迹链 / 标题显示群名 × 成员名）
- 三个临时调试探针（`__dbgTrace`/`__dbgPairViewSet`/`__dbgPairViewRead`）全部移除并复验 `undefined`

## 五、教训

1. **Vue 模板表达式内不要写 TS 类型断言**（`as X`）——编译器不保证语义，且失败形态是静默的空值而非报错。取值一律走事件签名 + script 侧处理。
2. **单测/构建全绿 ≠ 运行时可用**：本轮三个缺陷（断言取值、revision 陈旧、可发现性）无一能被现有测试捕获——UI 交付必须实地走查。
3. **建后必重启宿主**：改前端行/通道包后若走 public revision 分发，构建完需 restart_host 让宿主重扫清单，否则浏览器拿旧产物。
