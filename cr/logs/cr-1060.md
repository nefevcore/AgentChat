# cr-1060 会话路由与停止面双 bug 修复

- 日期：2026-11-13
- 状态：done

## Bug 1：切离新会话草稿位后，发送进了新会话而非所选会话

复现：点「新会话」（草稿位，选未分组/工作区解锁输入）→ 切到其他会话 → 发消息 → 消息落入新会话。

根因：`ChatInput.send()/sendNow()` 的草稿派发判据 `props.single && singlesBoard?.isPending()`。
`isPending()` 是全局单例草稿态（cr-848/894 裁决：未发送草稿跨切换保留），`props.single` 只要当前视角是 single 形态就非空——两个条件在「草稿留存 + 用户已切去别的独立会话」时同时成立，`dispatchDraft()` 抢先建会话并把上下文切到新会话，消息随之进错会话。

修复：判据改为「正站在草稿位上」——`props.single?.id === PENDING_SINGLE_ID && singlesBoard?.isPending()`（send/sendNow 两处；与 `freshWsGate` 的哨兵判据同款口径）。真在草稿位发送时行为不变（派发 + 切真值行）；在其他会话发送时草稿静默留存，消息路由到所选会话。

回归：`draft-single.test.ts` 新增静态对拍（cr-1058 同款手法）——断言两处判据都带哨兵 id 比较、旧判据字面不复存。

## Bug 2：发送后点停止，把同 Agent 其他正在运行的会话也停了

根因：前端 `chat-core.interruptGeneration()` 已按当前视角精确算好会话键（single = sid；1v1 直答 = `bucketKey(viewer, agent)` 对桶键），但宿主 `face-shell.ts` 的 `conversation/interrupt` RPC 处理器把 `conversationId` 参数丢弃——`shellCall(agentId, { ctrl: 'interrupt' })` 不带键，壳侧 `interrupt(undefined)` 的既有语义 = 中止该 Agent **全部**在途 run。

修复：face-shell 透传 `conversationId`（`optStr` 白名单窄化，缺席不携带 = 向后兼容旧语义）。键形态已核对：`pairKey`/`bucketKey` 同算法（sort+join('~')，与 web-api deliver 的键归一 cr-1059 同口径），壳侧 `gateKey` 对该键自算派生，透传即精确命中 `activeRuns` 单条目。

回归：`face-shell.test.ts` interrupt 用例补透传断言（带键帧含 conversationId；缺键帧不含）。
