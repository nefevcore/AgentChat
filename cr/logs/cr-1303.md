# cr-1303 contextBusy 跨会话串台根修

> 2026-11-24 · #conversation · 触发：cr-1302 真机重测后的现场复核。

## 现象

手机页在 designer 会话里，输入框主按钮恒显示「停止生成」（`stopping`），点击后消息
发不出去。页面无任何流式活动（frame/commits 零增长、内容不变）。

## 根因（真机实证，非推断）

`chat-core.ts` `contextBusy`：

```ts
const contextBusy = computed(() => {
  const id = feed.activeDialogId;
  const d = id ? feed.getDialog(id) : null;
  return d ? d.streaming : turnInProgress.value;   // ← 缺陷：无活跃会话时回落全局
});
```

`feed.activeDialogId` 是 computed：`activeSingleId → activeGroupId → roster 选中` 三级派生。
实测该页面三者皆空（移动端单会话导航态 / 选中被清空）→ **activeDialogId = null**；
而 `turnInProgress` 是**全局**忙态，会被**任何**会话的 run 点亮——本机实测页面 feed 里
同时存在 `pair:designer|user`（false）与 `single:01a20dc6…`（**true**，即另一会话的
实时 run，其流式帧确实到达了本页），于是回落分支让输入框跟着别人的 run 变「停止」。

后果链：`busySend = !props.onSend && store.contextBusy` → 按钮显示「停止」→
`onPrimary()` 走 `busySend ⇒ store.interruptGeneration()` 分支 → **消息根本不进 send 路径**
（不是「发了没到」，是压根没发）。

## 因果实证（真机，双向）

| 步骤 | 结果 |
|---|---|
| 修复前：把 `turnInProgress` 置 false | 按钮 `stopping` → `icon-btn send-btn`（**立即变发送**）——证明它就是唯一驱动量 |
| 修复后：页面存在别的会话 streaming=true（`single:01a20dc6` 实测 true）且 activeDialogId=null | 按钮仍为 `icon-btn send-btn` / aria-label「发送」——**不再串台** |

## 修法

```ts
const contextBusy = computed(() => {
  const id = feed.activeDialogId;
  if (!id) return false;                      // 无活跃会话 = 无可归属生成目标
  return feed.getDialog(id)?.streaming === true;
});
```

语义依据：无活跃会话时没有「本会话在跑」可言；此时点主按钮走 `send()`（空闲语义），
真忙由壳侧 ConversationMachine 的 lane 决策兜底（排队/steer 不会丢消息）。

## 与 cr-1302 的关系（结论修正）

cr-1302 的 e2e 实验②（restart_host + 不刷新 → 发送失败）**被本缺陷污染**：
执行实验时本会话（`single:01a20dc6…`，即 Agent 自己的 run）必然在跑 →
页面 contextBusy 恒真 → 点「发送」实际执行的是 interrupt → 消息从未进入发送链。
因此该实验**不能**证明「宿主重启后链路断裂」；「消息不落账」也被本缺陷充分解释。

仍成立的部分（另一条独立证据，不依赖页面）：宿主重启后 designer 壳被 dispatch 拉起
且 boot.ready 完成，但正本/inbox/journal 零写入、零 run——该现象需在**排除串台后**
重做 e2e 才能定性（cr-1302 已随之标注「待复测」）。

## 验证

- 新增回归锁 `tests/context-busy-isolation.test.ts` 3 例（无活跃会话不读全局 / 他会话跑不影响 /
  自身流式仍忙）——绿；
- 包内 400/400 ✓；typecheck ✓；定向 lint ✓（0 error）；
- 双构建（build:channel + webui:build）✓；真机端到端 ✓：`8+8=?` → 回复「16。」上屏、编辑器清空、
  收束后按钮正常回落「发送」（此时代页面 dialogs 里仍有他会话 `streaming: true` = 污染条件在场）。

## 运行时生效的关键坑（浏览器强缓存）

首次 reload（含 `ignoreCache: true`）后页面**仍执行旧代码**：产物里是新逻辑（`if (!id) return false`），
但页面 `store.contextBusy` 实测 true 且 `activeDialogId = null`——直接证明跑的是旧 bundle。

根因：通道产物文件名**固定**（`packages/ac-client-ui-conversation/client/dist/index.js`），
无内容哈希；MIUI 浏览器强缓存命中 → module loader 拿到旧文件。

解法：CDP `Network.setCacheDisabled(true)` + `Network.clearBrowserCache` + reload 后即生效
（复验：`contextBusy: false` / `sendBtn: icon-btn send-btn`）。

**教训**：改前端行后真机验证，光 reload 不够——固定名产物必须先清缓存，否则「测试绿 + 构建成功」
仍可能在看旧代码（与「双构建配对」事故同族的观测面陷阱）。

## 备注

诊断过程中曾直接写 `pinia.state.chat.turnInProgress` 做因果实验——该字段经 `toRefs` 委托，
直接写 state 会污染页面状态（一度让复验结果误判为「未修复」）；正确做法是只读或 reload 复位。
