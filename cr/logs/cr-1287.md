## 动机（§一 1.2 末段）

五个独立节拍交错：feed 同步直写 / markdown 自持 rAF + idle-commit setTimeout /
滚动引擎自持 rAF / 上翻补挂 setTimeout——闪烁节律不齐，且「每帧提交次数」
无处断言（P0-B 探针批搁置后更无观测面）。

## 实现

### 新模块 `client/frameScheduler.ts`

- **单 rAF 链 + 四阶段序**：`ingest → derive → commit → scroll`。同帧内各
  阶段任务按登记序执行、每阶段只跑一次；跨阶段顺序是构造性保证（提交先于
  滚动：本帧渲染出的新高度当帧即被滚动引擎看到，不再等下一帧）。
- **同帧自激防护**：任务内登记的同阶段任务被队列快照挡到下一帧。
- **单任务异常隔离**：一个任务抛出不影响同帧其余阶段（console.error 留现场）。
- **静默判据升调度器级**（§四原文要求）：`markActivity()` 单点维护活动时钟，
  `whenIdle(ms, cb)` 多订阅者共用同一「静止」判定（一次性语义），取代各 hook
  自持 setTimeout 各算各的静止。
- **持帧循环** `retainLoop()`：跟踪引擎等持续任务保活空转循环，释放即停摆。
- **提交探针** `noteCommit(idle?)` + `frameStats()`：`maxCommitsPerFrame` 即
  「每帧恰一次提交」的断言源（cr-258 P3 原始验收口径）；`idleCommits` 观测
  静默提交。

### 接入面（四节拍归一）

| 原节拍 | 现状 |
|---|---|
| feed 直写 | `feed-core.bump()` → `markActivity()`（ingest 活动打点，静默判据源） |
| markdown 自持 rAF | `useChunkedMarkdown.update()` → `scheduleFrame('commit')`；同帧多次 update 合并一次渲染（`scheduled` 标志），渲染点 `noteCommit()` |
| idle-commit setTimeout | `whenIdle(IDLE_COMMIT_MS, …)`——判据由 feed ingest / 组件 update 共享驱动 |
| 滚动引擎自持 rAF | `useChatShell` 全部 `requestAnimationFrame` → `scheduleFrame('scroll')` + `retainLoop()` 持帧；`stopFollow` 释放持帧 |
| 上翻补挂 setTimeout(16) | `TranscriptList.scheduleRefill()` → `scheduleFrame('scroll')`（与滚动同帧有序：补挂高度变化当帧被滚动修正吸收） |

`flush()` 语义保持：未执行的 commit 登记失效 + 立即全量渲染（流式收束终态）。

## 裁决

- **不引入通用调度库**（护栏 §三）：调度器只做阶段序 + 合并 + 探针，零依赖。
- **调度器不接管 Vue 响应式**：derive（turns computed）仍由 Vue 依赖登记驱动，
  本批只统一「何时写/何时提交/何时滚动」的节拍，不改派发模型——改动面收敛，
  流式语义零变化。
- **P0-B 口径复测维持搁置**（用户裁决 2026-11-24）：§九 基线表为空（无 desktop /
  Android 数字），真机场景暂缺；P4-2 按「每帧恰一次提交 + 流式回归 + 走查」
  收口，性能数字待有真机时补。状态板备注已写明。
- **写完即精简**：删 `cancelFrame`（无生产消费方——TranscriptList 用标志作废）
  与 `maxTasksPerFrame`（无消费读面），API 面只留四条接线点用到的导出。
