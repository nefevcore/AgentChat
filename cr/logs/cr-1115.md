# cr-1115 2026-11-15 结构消除 boot 窗口可达登记竞态

## 现场

```
23:31:10 [I] 拉起壳 tester：spawn pid=…
23:31:11 [W] outbox 转投失败（… → tester，已摘可达项，留箱待通道恢复）：connect ENOENT …ipc-tester-sock
```

冷启动壳 + outbox 滞留信在场时极易触发。

## 根因

壳 boot 序（apps/shell/boot.ts）：acquireActivationLock（早期，锁内已含
transportHint）→ 整段行集装配 → ipc listen。两事件间隔数秒 = **boot 窗口**
（manage 通道早有正式处置：cr-681 probeLiveShell 15s 窗口重试，「锁已持而
ipc 未 listen 的 connect 失败是窗口内常态而非故障」）。

宿主侧可达登记却以「锁在 + holder 活」为据（cr-885 语义），窗口内即登记
→ flushOutbox connect ENOENT → 被判端点死：摘可达项 + 「转投失败」W。
触发面 ×3：

- ensureHook 救援 `rescueReachableFromLock`（orchestrator.ts）
- peek 轮询 shell-emerged 分支（cr-748/cr-885）
- adoptLiveShells 接管登记（cr-967——adoptSocketShell 纯锁合成 adopted，不探 pipe）

cr-963 的 10s 补拉抑制只挡 flushOutbox 尾部 ensure 环，不挡上述登记面 →
可达表抖动 + W 刷屏（信不丢：at-least-once，adopted 转投兜底）。

## 改动

结构性收口：**「可达」登记一律以 pipe 实连为据，锁活只代表壳在 boot**。

- ac-envelope-core/src/ipc.ts：新增 `probeIpc(address)`——连上即断探针
  （listenIpc 对裸连接零语义，同 host-revive 既有用法）；2s 超时兜半开。
- apps/host/orchestrator.ts 三个登记面统一探连门：
  - rescue 返回三态 'ready' | 'booting' | null；ensureHook 异步化——
    'booting' 不登记、不冲刷、不 spawn（锁在必拒），滞留信由 adopted 转投
    与 poller 下拍兜底；
  - peek shell-emerged 分支探连通过才登记 + 冲刷 + 对账事件；
  - adoptLiveShells 探连通过才登记（窗口内跳过，poller 下拍收敛）。
- 删死代码 `liveShellHintOf`（rescue 改三态后无消费方）。
- 测试：既有 cr-647/cr-967 用例改真 listener（假 pipe 路径探连必败）；
  新增 boot 窗口回归（不登记不冲刷不 spawn；listen 后收敛）。

## 语义权衡（显式接受）

接管壳 boot 卡死（锁活、ipc 永不起）时不再有 W 诊断面：拉起中的壳由
adopt watchdog 兜（超时杀）；接管壳心跳断供由 supervise 判死链兜。窗口内
静默等待与 cr-681 manage 通道同口径。
