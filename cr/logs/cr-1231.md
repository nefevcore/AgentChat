# cr-1231 jitter 同刻度重投（neko t-pofx4t 一格投 5 次）

- 日期：2026-11-22　状态：done（代码已改，待宿主重启生效）

## 现象
`t-pofx4t`（every 7h30m + jitter 2h15m）同秒双投，间隔 22ms / 19ms / 113ms。

## 真机证据（workspace/home/meta/timer/audit.jsonl，13 条）
```
2026-11-21 07:13:49 | grid 07:30 | -16.2min EARLY  ×2（同秒双投）
2026-11-21 13:13:48 | grid 15:00 | -106.2min EARLY
2026-11-21 15:48:09 | grid 15:00 | +48.2min late   ← 同一刻度二次投递
2026-11-21 20:43:02 | grid 22:30 | -107.0min EARLY
2026-11-21 21:56:15 | grid 22:30 | -33.7min EARLY
2026-11-21 23:12:00 | grid 22:30 | +42.0min late   ← 同一刻度二次投递
2026-11-22 06:29:34 | grid 07:30 | -60.4min EARLY  ×2
2026-11-22 07:00:04 | grid 07:30 | -29.9min EARLY  ← 第三投
2026-11-22 07:01:10 | grid 07:30 | -28.8min EARLY  ×2  ← 第四/五投
2026-11-22 13:05:08 | grid 15:00 | -114.9min EARLY
```
13 条中 **11 条为负偏（early）**；07:30 刻度被投 **5 次**。

## 根因
`nextGridMs`（packages/ac-timer-core/src/index.ts）对 every 返回 `grid + rand*2J - J`。
抖动负偏时投递点可能落在**刻度之前**；此刻 `now` 仍早于该刻度，投递完重算
（`fireInner` → `arm` → `nextGridStrict(t, now)`）又返回**同一个刻度** ⇒ 同刻度反复投递。
若某次候选落在过去，`schedulePlan` 的 `wait = max(due-now, 0) = 0` ⇒ 立即投递，
与上一条叠成同秒双投。

## 修法（两道，缺一不可）
1. **刻度消费判定**：`lastFiredAt` 落在本刻度抖动窗内（`|lf - grid| <= jitterMs`）⇒ 该刻度已消费，`grid = nextGridStrict(t, grid, ctx)` 取下一格。
2. **不得回到过去**：`cand > now ? cand : grid`——越界退化为刻度本身（仍严格在未来）。

只在刻度生成侧修；**不在 dispatch 层去重**（那只是掩盖症状，会让「已投递但记账未推进」的堆叠隐藏起来）。

- 用例 cr-1231③（正常晚投不误跳下一格）：防过度修复的约束用例，新旧皆绿（非回归用例）

## 残留边界（两条，均已确认存在、均未修）

**① catchup 后误跳一格**（我自己实现时发现，不是已知修好的）
刻度消费判据用 `|lastFiredAt − grid| <= jitterMs`，但 **catchup 投递**的 lastFiredAt 是「补投那一刻」，与它对应的刻度并无抖动关系：
```
every 30m jitter 5m；09:30 刻度因进程停机错过；09:58 重启 → catchup 补投 09:30
lastFiredAt = 09:58；next grid = 10:00；|09:58 − 10:00| = 2min <= 5min ⇒ 误判「10:00 已消费」→ 跳到 10:30
```
代价 = **少投一格**（非重投）。仅在「jitter + missed: catchup-once + 停机跨刻度」三者同时成立时触发；默认 `missed: skip` 不触发。彻底修需把「已消费刻度」显式落状态（`lastFiredTick`），改动面大于本次。

**② catchup 判据仍用 lastFiredAt 作下界**
`lastDueMs` 未感知「刻度已消费」：若负偏提前投递后进程重启、且条目配 `missed: catchup-once`，该刻度会被判「错过」再补投一次（这次是重投）。默认 `missed: skip` 不受影响。

两条都指向同一件事：**「已消费刻度」这个概念目前只从 lastFiredAt 反推，没有显式状态**。本次修复在该前提下取了风险最小解；要做干净，应由 timers-row 记录 `lastFiredTick` 并入 DeriveCtx。

### 三条判据方法学教训（本轮付出代价换来的）

**① 网格归属由 arm 时刻决定，不是投递时刻、也不是 persisted 的 `armedAt` 字段。** 本机 `armedAt` = 11-21 00:26:51，比实际 arm（23:44）早 23.5h，用它算采样格得 11-21 07:30、偏差 +2750min 的荒谬值。arm 时刻须取「那次 re-arm 的宿主 boot」。这属于「取错对象」错误类——两个候选都真实存在、格式合法，选错语义。

**② 「负偏」不是鉴别点，`|lastFiredAt − ngs(lastFiredAt)| ≤ jitter` 才是。** 判「本刻度是否被新代码消费」用的 grid 是 `ngs(投递时刻)`（=07:30），不是采样格（06:00）。可鉴别区间是投递点 ∈ [05:15, 07:30)：下界 = 07:30−135min，上界 = 07:30（此时 ngs 跳到 15:00，|7.5h|>135 不消费）。早于 05:15 的负偏样本虽会复现旧 bug，但新旧同位不可分。

**③ 要防的是假绿不是假红。** 原以为「投递后重启会覆盖 nextAtCache 导致假红」，实际消费判定用 persisted `lastFiredAt`，新码在任何时刻重启都稳定产出 [12:45,17:15]；真正失效在反方向——boot ∈ [07:30, 15:00) 时 `ngs(now)` 直接返回 15:00，**旧码不消费本格也照样拿 15:00 当 grid**，与生效同形。故前闸须为 `boot < 07:30`，写成 `boot ≤ 投递时刻` 会误废 05:25~07:29 的有效窗口。

### 残余（不影响本次结论）

「已消费刻度」仍只从 lastFiredAt 反推、无显式状态 `lastFiredTick`；本报告开头列的 ①②两条残余风险（catchup-once + 停机跨刻度）依然存在，仅默认 `missed: skip` 不受影响。
## 第三重独立证据 · 按刻度分组计数（2026-11-23 14:30 核验，成立）

前面两条证据（nextAtCache 区间、audit 无双投）都是「单点观测」；本条直接观测原 bug 现象本身：**同一刻度被投几次**。

```
05:20:58  grid 07:30  -129.0min  ← 消费 07:30 刻度（宿主 23:44:09 boot 采样）
14:02:58  grid 15:00   -57.0min  ← 消费 15:00 刻度（宿主 10:15:06 boot 重采样后落到此处）
nextAtCache = 11-24 00:06:01     ← 落 [20:15, 00:45]（22:30 刻度窗）
```

**07:30 刻度投 1 次、15:00 刻度投 1 次，无任何刻度被投第二次。**
旧码在该刻的必然行为：14:02:58 投完后 `nextGridStrict(14:02:58)` 仍返回 15:00（此刻早于刻度）
⇒ grid 保持 15:00 ⇒ 候选 ∈ [12:45, 17:15] ⇒ **17:15 前必再投一次**。实测未发生，且 nextAtCache
已推进到 22:30 窗，两区间互斥（00:06:01 高出旧码上界 171min）⇒ 新码消费了 15:00 刻度。

**样本更新说明**：原计划观测的 13:23:54 被 09:52 / 10:15 两次宿主换代的 re-arm 重采样改写为 14:02:58。
这不是样本丢失而是换到更优样本——原 13:23:54 只是「区间落点」，新样本 14:02:58 是**负偏**（−57min），
正是走修复路径的那种投递（正偏样本根本不触发 bug，鉴别力为 0）。
