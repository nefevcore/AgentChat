# cr-1314 壳 boot 死管道 EPIPE 防护前移 main 入口（接管代子代理 spawn 四连崩）

## 现场（sandbox/diag-subagent-crash-2026-11-25.md）
2026-11-25 上午 11:36/12:13 四次 subagent spawn 全退 1（exit code=1 signal=null），无终稿。
children/<sub-id>/ 物化域齐备（agent.json/agent.patch.yml/auth.json/boot-graph.json/中拍
boot-progress rows 在、fingerprintRoot 无、inbox 任务信落盘）——boot 死在中拍（L946）
与终拍（L1287）之间；无 messages.jsonl = run 从未开始。下午 14:32 restart_shell 后三连正常。

## 根因
1. 10:57 restart_host → 宿主 exit 42 优雅换代；新宿主 adoptLiveShells 接管活壳（锁/路由），
   但 stdio 管道不重建——本壳 stderr fd 仍指向已死旧宿主的管道；
2. 本壳 spawn 子代理：ac-shell-subagent defaultSpawnShell stdio stderr='inherit'——子壳
   继承本壳的死 stderr fd；
3. 子壳 boot 中段首个 process.stderr.write → EPIPE（异步 error 事件，此时 cr-612 的
   stdout/stderr error 挂钩尚未执行——挂在 main() 尾部 L1494-1495，bootShell 完成后）
   → uncaughtException → exit 1；
4. 本壳自身上午不写 stderr 故存活，只有高频写 stderr 的子代理批量崩——与观测吻合。

## 修复
挂点前移：main() 入口（argv 解析前）即挂 process.stdout/stderr error handler——写死管
静默吞，壳照常跑（cr-612「宿主死后管道断裂写必须不崩」的本意，只是挂的位置太晚——
护不住 bootShell 中段的诊断写）。两处编辑：入口新增 + 尾部旧挂点注释指向新位置。
辅修（诊断文档建议项）不采：stderr='inherit' → 'ignore'/pipe 会切断子壳诊断线；且主修
后 inherit 耦合面（死 fd + EPIPE 被吞）自闭环，无残留故障面。

## 验证
- Windows 探针实证（sandbox/probe-epipe-*.mjs，事后清理）：无 handler 子进程死管写
  exit 1 / 挂 handler exit 7 正常收——回归测试触发面有效；
- 回归测试（apps/shell/tests/boot.test.ts 进程级冒烟 describe）：spawn 真壳 → 掐死
  stderr 读端 = 死管形态 + shell.patch.yml 顶层非数组（readAssemblyPatch 警告 = 锁后
  确定性中段 stderr 写）→ 断言 boot 照常完成（终拍 fingerprintRoot 落盘）+ manage
  shutdown 优雅退 0。修复前该用例死（uncaughtException exit 1）；
- 阶梯：pnpm typecheck / test:unit / check:deps / eslint 定向 / test:integration。
- 运行时生效：restart_shell（apps/shell = 宿主 spawn 的壳进程源码——进程换代装载新码）。

## 验收自答
根因 = EPIPE 防护挂点在中段 stderr 写之后；修复 = 前移挂点至进程入口，护住全程。
与文档根因链第 4 步因果同源（文档落点：boot.ts L1494-1495 挂钩前移 main 入口）。
