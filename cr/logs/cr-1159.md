# cr-1159 restart_shell 多会话并发单槽修复

## 动机（缺陷分析结论）

同一壳内两个会话同时发起 restart_shell 时，通知链端到端单槽——另一个会话（甚至发起方自己）永远等不到「已重启」唤醒。四层证据：

| 层 | 位置 | 修复前事实 |
|---|---|---|
| 工具行旗标 | ac-shell-rows/src/restart.ts | `shellRestartScheduled` 壳级单布尔：第二发起方被吞，返回 alreadyScheduled，其会话键从未登记 |
| 服务意图 | ac-shell-conversation/src/service.ts | `restartPending` 单布尔；`requestRestart()` 无参——发起方键在工具边界即丢弃 |
| 落盘 marker | apps/shell/boot.ts | `restart-shell/<agent>.json` 只存一个 `conversationId` |
| 新壳注入 | apps/shell/boot.ts | 单变量单次注入「已重启」 |

关键缺陷：`restart-ready` 携的 conversationId = 最后收束的 run 的会话键（service.ts driveRun 收束点 `uuid`），与谁发起无关。

三个场景：
1. 两会话并发各调 → 后收束者（设 B）键进 marker，只向 B 注入；A 滞留到下一条外部消息（与 cr-994「等来件」同形）。
2. 仅 A 发起、无关 run 的 B 最后收束 → 通知错投 B（多余开跑轮），A 等不到。
3. reviewRun（机制 run）最后收束 → `restartPending` 孤儿化：无 restart-ready、无 marker、不退 42 → idle-exit(0) 判 done 不重拉，重启静默蒸发。

排除项：driveRun 双检查竞态不可达——检查点→finally 删除之间同步无 await，单线程恰好一个 run 观察到「size≤1 且自己还在」。

## 修复（通知链四层改多键）

1. **service.ts**：`restartPending` 布尔 → `restartOrigins: Set<string>`；`requestRestart(conversationId?)` 登记发起方键；driveRun 收束点全闲检查（`origins.size>0 && activeRuns.size<=1`）携键集 emit；reviewRun finally 补同构检查（孤儿化收口——drainQueuedTurn 唤醒的链跑若已兑现则幂等跳过）。
2. **events.ts**：`'conversation/restart-ready'` payload `conversationId?` → `conversationIds?: string[]`。
3. **restart.ts**：行旗标 `Set<string>` per-conversation；execute 接 `call.conversationId` 透传；RestartFace 签名同步。
4. **apps/shell/boot.ts**：marker 落盘 `conversationIds`（空集照写——无发起方语义 = 旧空闲直发形态）；boot 自清读键集（兼容旧单值 `conversationId` 字段——存代壳写的 marker）；「已重启」注入改逐键循环（串行，注入不插队语义保持）。

宿主侧 `sweepRestartShellMarkers` 只读 marker 的 `at` 做 TTL、takeover `consumeRestartMarker` 只透传原文——对内容零依赖，零改动。

## 兼容性

- 旧代壳写的 marker（单值 `conversationId`）新壳可读（Set 去重兼容）。
- `requestRestart()` 无参调用兼容（测试/外部调用形态——键集为空则空集直发）。
