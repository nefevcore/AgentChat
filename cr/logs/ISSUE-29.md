# ISSUE-29 静态命令扫描无法约束脚本执行（架构级，2026-11-22）

## 结论

**逐条补正则的路径扫描不可能收敛。** ISSUE-28 修了 5 条（引号包覆 / `./` 前缀 /
路径中段 / 换目录别名 / 选项前缀 / 裸 `..`），每条都是真缺口、每修一条都对；
但换一种执行形态仍然可绕——因为扫描的是**命令串字面量**，不是**运行时实际访问**。

## 证据（tester 实测并如实上报）

```js
// 在 cwd 写 scancheck.mjs，内容 import 沙箱根之外的模块
await import('../../../../packages/ac-sandbox-core/src/index.ts');
```
```
node scancheck.mjs  → 成功执行
```

命令串 `node scancheck.mjs` 不含任何越界路径字面量 ⇒ 扫描放行；脚本体内的任意
`fs.readFileSync` 不受约束。

同机不一致：

| 命令形态 | 结果 |
|---|---|
| `git -C <仓外路径> status` | 拦（命令串含路径字面量） |
| `node <任意脚本>` | 畅通（命令串无路径字面量） |
| `python <任意脚本>` | 畅通（同上） |

**拦截强度取决于命令形态，不取决于实际访问的路径**——这个不一致本身就是问题陈述。

## 为什么补正则解决不了

绕过面随执行形态增长：解释器（node/python/pwsh -File）、管道、重定向、
`$(...)` 子命令、变量拼接、`eval`/`Invoke-Expression`、配置文件驱动（如 dotnet/npm
读取的配置里写路径）…每种都要单独列规则，且规则之间总有缝隙。

ISSUE-28 的五条修复价值在于**把常见形态堵住**（尤其 `./../../x` 这种人的自然写法），
但不构成安全边界。

## 建议方向（未实施，需决策）

1. **运行时层约束**（根治）：受限 job（Windows Job Object / 低权限令牌）、
   或容器/wasi 执行环境，让越界访问在 OS 层失败——不依赖命令串解析。
2. **解释器类命令单列策略**：`node`/`python`/`pwsh` 等执行脚本的命令，
   校验脚本文件本身在允许根内（当前 `node scancheck.mjs` 里 mjs 在 cwd 内，
   所以这条只能约束「脚本位置」，不能约束「脚本行为」——半步）。
3. **能力面收敛**：不给非必要 Agent 开 shell 能力，比补正则更有效。

## 与 ISSUE-28 的关系

ISSUE-28 是「命令串扫描的规则完备性」——本文件是「命令串扫描本身的能力上限」。
两者不同层，不可互相替代。ISSUE-28 已修 5 条并全部回归覆盖；本文件记录的是
**该机制无法覆盖的部分**，以免后人误以为修完 ISSUE-28 就安全了。
