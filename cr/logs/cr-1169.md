# cr-1169 源触发 lastSeq 持久化缺失修复（同 seq 重投）

> 登记于 2026-11-20 · →cr-1165（采集层——源触发运行时实现缺陷）· 状态：done

## 动机（news 实测反馈）

news 报「同一 seq 触发了两次」。审计行铁证：`t-xzwnfr` 的 `seq:10` 在 11:44:52 与 12:05:12 各投一次；12:05:02 是宿主重启时刻，12:05:12 = pull 兜底首扫（interval 10s）。

**根因链**：首次投递后 lastSeq 推进到 10（仅在内存 `lastSeqByEntry`）→ 宿主重启内存丢失 → pull 首扫发现 `meta.seq(10) > lastSeq(0)` 判「落后」→ 重读全部 10 行 → match 命中 + cooldown 也随内存丢失 → 二次投递。

**违反设计**：timer-v3 §六防线表明写「重启 | nextAt / lastSeq 落 state.json；源触发按 lastSeq 续读」——cr-1165 实现了记账 Map 却没接持久化。

## 改动面

- `TimerPersistedState` 加 `lastSeq: Record<source/view, seq>` 字段（随既有 state.json 原子写链路落盘）。
- `lastSeqOf / advanceLastSeq` 改读写 persisted（删内存 `lastSeqByEntry`）；advance 即时 saveState。
- **matchAndFire 读后即占位**：读行 → 先推进 lastSeq（maxSeq）→ 再投递。防「投递是异步的，投递完成前窗口期内的 pull/后续事件重读同批行」并发双投；投递失败不回退（at-least-once 由邮局 outbox 承担——与时间触发记账语义一致）。
- cooldown 保持内存态（重启丢失无害：lastSeq 已持久化 = 无新行可重投，cooldown 只是节流瞬态）——原注释补此裁决。

## 验证

- 新增回归测试「重启续读」：投过一次 → dispose 模拟重启 → 断言 state.json 含 lastSeq 断点 → 重 boot → 同 seq 事件不投（received=0）。
- timers-row 16/16；typecheck / 定向 eslint 绿；全量 455/455 绿。

## 裁决

- 重启幂等的记账锚 = lastSeq（持久）；投递节流 = cooldown（瞬态）——两者生命周期分离，不捆绑持久化。
- 读后即占位 vs 投后推进：选前者——双投窗口（危害 = 重复唤醒）大于漏投窗口（邮局 at-least-once 已兜）。
