# cr-1050 goal 驱动两修：壳侧 meta 贯通 + 等待态门

## 背景（两问题）

1. **Round 无自增**：goal-round 轮次恒 1/N，maxRounds 永不到达。
2. **等待态照催轮**：run 收束即投下一轮，模型刚派的 job/子 Agent 还在跑，新轮只能空转或重复派活。

## 根因

### 问题 1：壳侧 conversation 断链

ac-goal 的轮次记账判据 = `loop/after-run` 的 `request.meta[GOAL_ROUND_META]`。
投递链：`GoalsService.deliverNextRound → conversation.deliver(meta) → 信封 → agentLoop.run(meta) → loop/after-run`。

- 主线 ac-conversation（`startRun → router.send`）meta 全链贯通——测试组合下工作正常；
- **生产实跑的是壳侧 ac-shell-conversation**：其 `deliver()` 签名无 meta、构造信封时丢弃，
  `driveRun` 装配 `agentLoop.run` 请求也无 meta 字段 → `request.meta` 恒 undefined →
  记账恒不触发 → roundsDone 永不 +1。

### 问题 2：驱动无等待态判定

`maybeContinue` 在 run 收束点无条件投下一轮，不看本 Agent 是否有在途 job / busy 子 Agent。

## 修复

### 修 1：壳侧 meta 贯通（ac-shell-conversation）

- `deliver()` options 增 `meta`；两处信封构造写入 `payload.meta`（跨壳投递同样透传）；
- 新增 `payloadMetaOf(env)`（白名单窄化：非对象视同缺席）；
- `driveRun` 装配 run 请求时注入 `...(meta !== undefined ? { meta } : {})`（链跑轮各取当轮信封）。

### 修 2：等待态门（ac-goal）

- 新增 `activeWaitOf(ctx, agentId, conversationId)`：jobs.list(agentId) 有 running/stopping，
  或 subagents.listOp(conversationId) 有 busy 子 → 返回等待描述；软依赖（行缺席 = 无等待态照常投递）。
- `maybeContinue` 拆出 `deliverNextRound`（active 判定 + 等待门 + 投递单源）；
- 等待门不阻塞：job 完成通知回投 → 唤醒 run → 收束点再评估门，门开即投；
- `job/settled` 补位监听：**仅 owner 自杀形态**（killedBy=owner 且非 failed——wakeup 不通知该形态）
  由本面补投下一轮；正常完成的通知 run 收束会自然续推，此处再投只会 steer 注入浪费执行。
