# cr-1046 邮局 dispatch 失败静默吞 + ipc 无超时 → done-reply 回信永挂、三壳 activeRuns 泄漏

## 现象
- 前端「运行跟踪」三个会话（designer~news / neko~neko / news~news）显示运行中十余小时。
- 宿主 runs/snapshot 的 running 与壳 run-state 的 runs 一致泄漏；同 run 同时出现在 recentSettled（早已 finish=ok）。
- news 壳 queuedTurns=20（30 分钟一轮的热点轮巡信积压无人消费）。

## 根因链（三层）
1. **语义层**：子 Agent 完成回执（done-reply）唤醒的自会话/跨壳 run，终稿 postReply(to=user) 的信封 uuid 沿用原会话键（如 news~news）。邮局 routeEnvelope 以 [sender,to]=[news,user] 做 registry 参与者校验，与首封信的 [designer,news] 登记集「交叉不包含」→ conflict throw。
2. **传输层 A**：listenIpc 的 onFrame reject 分支静默吞错不回帧（注释自称「发送方超时重发兜底」，但该超时从未实现）。
3. **传输层 B**：IpcClient.request 无超时——回帧永不到达即 promise 永挂。

三层叠加：postReply 永挂 → driveRun 的 finally 永不执行 → activeRuns 泄漏、busy 永真 → 链跑队列死寂。

## 修法（断根三处）
1. `ac-envelope-core/ipc.ts`：onFrame reject（含同步 throw）→ 回 `__ipcReject` 错误帧；request 收错误帧转 reject；request 加缺省 15s 超时（timeoutMs 可覆盖）。任何 dispatch 失败从此可达发送方，重试面真正生效。
2. `ac-shell-conversation/service.ts` postReply：投 user 的终稿通知 uuid 改用 `pairKey(agentId, 'user')` 对桶键——语义正确（这是 user⇄agent 通道上的通知）；1v1 会话两键同值行为不变。registry 防线语义不动。
3. 回归测试：ipc-cr1046（错误帧/超时/谓词穿透）、registry-cr1046（conflict 防线不放宽）、service.test cr-1046（对桶键 e2e）。
