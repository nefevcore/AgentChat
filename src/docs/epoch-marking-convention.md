# 注释时间标记规范（epoch-marking）

> 本文确立 `YYYY-MM` 时间标记的语义与书写规范。存量标记与真实日历月存在系统性偏差
> （详见下文「溯源」）——偏差是历史事实，规范只管**今后怎么写**，不做全量回改。

## 一、现状与偏差事实（为什么会有这份文档）

2026-09-20 核查结论：

| 证据 | 内容 |
|---|---|
| 当前真实日期 | 2026-09-20 |
| git 最后提交 | 2026-09-19 |
| HEAD 已提交代码中的标记 | 2026-10 x63 · 2026-11 x187 · **2026-12 x110**（全部超前于真实日期） |
| 首次引入溯源 | 2026-12 首现于 2026-09-13 提交；2026-11 首现 2026-09-05；2026-10 首现 2026-08-31 |

偏差成因：设计文档/计划在编写时把**预期完成批次**标成了未来月份（如 access-tier
规划标「2026-12」、抉择组规划标「2026-12」），实现随后跟进时注释**原样携带计划里的
纪元标记**。于是仓库时间线形成了一个自洽但超前于日历的「计划纪元」——同一特性从
计划到实现到注释都沿用同一个（未来的）月份词。

## 二、语义定义（今后如何解读）

**`YYYY-MM` = 特性批次代号（epoch），不是落笔日历月。**

- 标记回答的是「这个改动属于哪个设计批次/裁决代际」，不是「哪天写的」。
- 同一批次的机制在注释中共享同一个标记（如 access-tier 的多个文件都标 2026-12）——
  这是有意为之：时间线语义依赖批次一致性，单独改某个文件的标记会制造
  「先于它所依赖的机制」的假时间线。
- 真实落笔时间以 git blame 为准，注释不承担这个职责。

## 三、书写规范（今后如何写）

### 规则 1：新批次沿用「计划纪元」——标记 = 该特性计划文档所标的批次

改动若源自某份计划/设计文档（docs/ 里的 plan/report），注释标记**照抄计划文档
所标的批次**，不按落笔当日日历改写。

```
// 正确：access-tier 计划标 2026-12 → 实现注释也写 2026-12（即使当天是 9 月）
// 错误：同批实现注释写 2026-09 —— 与同批其他文件断裂，制造假时间线
```

### 规则 2：无计划文档的即兴改动 —— 标记 = 真实日历月

不是源自计划的修复/小改（如 bug fix、注释勘误），用**落笔当月**。既然是即兴
批次，它没有计划纪元可对齐，真实月份就是它的批次号。

### 规则 3：一个特性一个标记，中途不换

特性跨多次提交演进时，标记从首笔定到收尾——后续追加的注释沿用首笔标记。
若确需区分阶段（如「2026-09 立项 / 2026-12 重构」），两个标记并列书写，
各自锚定各自的事实。

### 规则 4：禁止「顺手统一」存量标记

存量 300+ 处超前标记（2026-10/11/12）**保持原样**：
- 全量校准需重写 300+ 处、污染 git blame、且要逐处判断「计划纪元 vs 笔误」，
  成本远超收益（全量校准方案已在 2026-09-20 评估否决）；
- 它们彼此自洽（同批同标），按第二节语义解读无歧义；
- 仅当**顺手修改同一文件的该行注释**（本来就要动它）时，才可顺带把该行标记
  校正为该特性计划文档的批次——不为此单独开改动。

### 规则 5：文档名/路径中的日期是**命名**，永不回改

`docs-stale-2026-12\`（归档根路径）、`run-code-usage-profile-2026-09-20.md`
（画像文档名）等——日期进了标识符就是身份的一部分，改名 = 破坏外部引用，
与内容是否「过期」无关。

## 五、速查

```
看到注释里的 2026-12 →
  读作「2026-12 批次的特性」（计划纪元，不是 12 月才写的）
写新注释 →
  有计划文档 → 照抄计划批次标记
  无计划即兴改 → 写真实当月
  改存量注释（本来就要动那行）→ 顺带对齐该特性批次；不动则不碰
```
