## 一、事故时间线（7 次 edit 调用的完整复盘）

目标：将 `TagCatalogEntry.reserved` 字段的 JSDoc 从"base 已退役（全量标签化 2026-09-16）"精简为"base 已退役"，**并预期不动其他任何行**。

| # | 意图 | 实际效果 | 破坏形态 |
|---|---|---|---|
| 1 | 改 JSDoc 措辞（fuzzy=0 精确匹配） | ✅ 成功 | — |
| 2 | 再改措辞（第二次） | ✅ 成功 | — |
| 3 | 第三次微调措辞 | ✅ 成功 | — |
| 4 | 第四次微调 | ✅ 成功 | — |
| 5 | 第五次微调 | ❌ **old_string 精确匹配失败**（措辞已与前次产物有细微出入） | 触发 fuzzy 归一化路径 |
| 6 | 恢复误删的 declaredBy 字段 | ❌ **`reserved?: boolean;` 字段本体被删除**（JSDoc 行与字段行作为整体被替换掉了字段行） | 结构损坏 ① |
| 7 | 恢复 reserved 字段 | ❌ **`const RESERVED = [` 声明行被删除 + interface 体内残留 RESERVED 声明** | 结构损坏 ②（跨块污染） |

随后又发生两次同类事故（补闭括号产生重复 `}`；恢复声明行后 interface 内残留旧声明），累计 **4 次结构性损坏、约 12 次 pwsh 修复操作**。净结果：一个 21 insertions/8 deletions 的注释级改动，消耗了 **19+ 次工具调用**。

**关键放大因素**：该文件存在大量同前缀重复文本——同一 JSDoc 注释块（`/** 预注册词（档位与能力族；base 已退役...`）在连续微调中产生了多个彼此仅差几个字的版本；`const RESERVED: Array<...> = [` 声明行在文件中出现两次（一次误插进 interface、一次在正确位置）。

## 二、根因分析（对照 ac-edit-core 源码）

### 2.1 设计缺陷 #1：模糊匹配（fuzzy-match.ts）没有唯一性护栏——跨级不对称

`fuzzyFindText`（`src/ac-edit-core/src/fuzzy-match.ts:41`）的三级策略：

```
Level 0: 精确 indexOf
Level 1: NFKC + trimEnd + smart-quote/dash/space 归一化
Level 2: NFKC + trim（行首行尾全去）
```

对照 `applyEditsToNormalizedContent`（`apply.ts:62-82`）的校验逻辑：**唯一性检查只在「选定级别」内做**（countOccurrences 用同级归一化形态计数）。这意味着：

- Level 0 精确命中后，Level 1/2 的潜在多命中**不再检查**——这本身正确（精确命中优先）；
- 但 Level 1 命中后（`apply.ts:63-72` 用 Level 1 归一化形态计数，occurrences=1 通过），**Level 2 视角下可能存在多处命中**——归一化越激进，文本折叠越厉害，"唯一"的判定越宽松。

事故中的实际机制：第 5 次 edit 的 old_string（自拟措辞，与文件实际内容有空白/措辞差）走 Level 1/2 归一化命中。归一化把**行尾空白、行首空白**全部抹掉后，同前缀的多个 JSDoc 版本块在归一化空间里**彼此重叠/趋同**，匹配滑到了非预期位置（edit 返回 `fuzzy_matches: 1` 但 diff 结构异常——见输出字段 `fuzzy_matches:1` 的事故轮次）。

### 2.2 设计缺陷 #2：LLM 调用方的 old_string 自拟文本是模糊匹配的放大器

系统提示词纪律明确要求"old_string 从 read 的输出中原样复制（自拟文本会匹配失败）"——这条纪律的隐含假设是**匹配失败是安全的**（fail-closed）。但 fuzzy 归一化让"自拟文本"有相当概率**匹配成功到错误位置**：

- 精确匹配时代：自拟 → 找不到 → 报错 → 重新 read → 安全
- 模糊匹配时代：自拟 → 归一化后命中重复文本段的某一处 → **静默替换错位** → 结构损坏

事故链正是如此：连续 5 次对同一段注释微调，第 5 次的 old_string 已是"记忆中的上一次产物"而非 read 原文——Level 2 trim 归一化让它命中到了相邻块。

### 2.3 设计缺陷 #3：替换是字符串切片，无语法层校验（apply.ts:111-116）

```ts
result = result.slice(0, index) + edit.newText + result.slice(index + matchedLen);
```

替换后的内容**不经任何语法检查**（括号配平、AST 可解析性）直接进入 diff/写回管线。TS 文件损坏（interface 未闭合）要到下一次 typecheck 才暴露——而那时 LLM 已经基于损坏文件继续编辑，形成二次破坏。事故中"闭括号丢失 → 补括号 → 重复括号 → 去重 → 又删声明行"的连环事故正是**无语法校验 + 无编辑隔离**的复合效应。

### 2.4 设计缺陷 #4：重复文本场景下唯一性报错信息的恢复指引失效

`apply.ts:74-82` 的重复报错建议"在 old_string 中多包含前后几行内容"——但当文件里存在**归一化后趋同的重复块**（如事故文件的多个 JSDoc 版本）时，扩大上下文反而**把更多重复内容包进来**，唯一性进一步恶化。恢复指引在这种场景下形成死循环：越改越不唯一。

## 三、修复建议（按优先级）

### P0 · fuzzy 命中降级为「需确认」事件（匹配语义收口）

模糊匹配的存在理由是消除 LLM 的 Unicode/空白噪声——但**噪声吸收不应以静默错位为代价**。建议：

1. **Level 2 命中即拒绝编辑，返回"匹配歧义"错误**（要求 read 原文重试）——Level 2 的 trim 归一化在重复文本文件里错位率过高，收益不抵风险；Level 1（trimEnd + 引号归一化）保留，覆盖 Unicode 噪声主场景
2. 唯一性检查升级为**全级别交叉校验**：选定级别命中后，再以更激进级别复查出现次数——归一化空间里 >1 即要求扩大上下文
3. 报错信息附带**归一化空间的 diff 提示**（"归一化后与 N 处文本趋同，请复制 read 原文"），替代现行的"多包含上下文"指引（重复块场景下会恶化）

### P1 · TS/JSON 文件写回前语法校验（fail-fast）

`applyEditBatch`（executor.ts:78）写回前，按扩展名做轻量校验：

- `.ts/.vue`：括号配平预检（成本 O(n)）或 `ts.createSourceFile` 快速解析
- `.json`：`JSON.parse`
- 校验失败 → **拒绝编辑、文件保持原状**、错误指引"old_string 匹配错位，请 read 后重试"

本事故若有此护栏，第 6/7 次的结构损坏会在写回前被拦下，连环事故链在第一环即断。

### P2 · 编辑后 read-back 回显（反馈回路补强）

edit 工具结果中附带**编辑区上下文的 read-back**（前后各 3-5 行 + 行号），让调用方（LLM）能立即核对自己的编辑落点是否正确——当前 diff 输出在结构损坏时依然"看起来正常"（diff 是编辑引擎自算的，损坏内容照样生成 diff），调用方无从察觉。

### P3 · 调用方纪律补强（系统提示词）

现有指引"old_string 从 read 的输出中原样复制"补充场景化警示：**连续编辑同一文件段落时，old_string 必须重新 read 获取**（上次编辑的产物 ≠ 记忆中的文本）；文件存在重复/相似文本块时优先用 pwsh/write 整段重写而非 edit。

## 四、方法论沉淀（对本次事故的调用方教训）

1. **同前缀重复文本段是 edit 的雷区**：连续微调同一注释块会产生"归一化趋同"的多个版本，fuzzy 匹配在此类文件上不可信——此类改动应直接 write 整文件或 pwsh 行级操作
2. **edit 的 fuzzy_matches>0 是危险信号**：工具结果里的 `fuzzy_matches: 1` 字段意味着走了归一化路径，编辑位置可能有偏差——值得在结果里升级为更显眼的警示
3. **修复被 edit 损坏的文件时不要再用 edit**：损坏文件的结构异常会让后续 edit 的匹配进一步漂移（事故第 6→7 次的恶性循环）；正确动作是 pwsh 行级修复或整段重构
4. **小改动预期与工具调用次数的失衡是早期信号**：本事故中"改一句注释"预期 1 次调用，第 5 次仍未收口时即应止损换工具——实际拖到第 7 次后连环损坏
