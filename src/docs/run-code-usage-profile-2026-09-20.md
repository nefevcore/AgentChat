## 优化线索（按痛点排序）

### ① 单行 425KB——收束行结构性膨胀
- 现象：messages.jsonl 2.5MB / 70 行（均值 36KB/行）；最大收束行 425KB
  含 13+ run_code 调用对（单对 arguments 0.2-1.3KB + result 5-9KB）。
- 根因：收束行 steps 携带整轮全部调用对（KV 前缀保真语义）。读操作
  （read/grep 的文件内容全文）对回放有价值但体积大头。
- 方向：steps 按工具类分层——写操作全量、读操作 result 降为摘要/偏移。
  动 KV 语义，需单独立项权衡（跨轮命中损失 vs 存储减半）。

### ② 失败形态集中——可擦除 TS 的 DX 税（纯收益，优先做）
- 8/14 失败 = 「程序体类型擦除失败 Expected ',', got 'ident'/'string
  literal'」——全部是模板串嵌套/含 \n 字面量被传输层转义破坏。占失败 2/3。
- 方向：worker 预检错误带【行列 + 最近 token + 修复建议】；SDK 投影
  （DEFAULT_GUIDANCE）加模板串转义显式示例；可选：程序体传入前服务端
  做常见转义形态探测告警。

### ③ edit 匹配失败退化为 pwsh——写路径成本隐性上升
- 现象：edit 218 次之外，pwsh 256 中相当部分是「读文件 + 行级替换」
  ——edit 的 old_string 在 CRLF/转义层消耗上反复失配（本会话 ≥6 次退路）。
- 方向：edit 失败信息附带【最接近的实际行内容 + 差异位置】；old_string
  对行尾差异做显式归一化提示（不静默模糊匹配——保留现有防错语义）。

### ④ subcalls.jsonl 1898KB——读操作结果全文在档
- 现象：782 子调用全文落盘（UI 回放档案语义），read 189 次的文件内容
  全量在内；已接近主文件体量。
- 方向：归档压缩 / UI 投影按需加载（偏移量记录而非全量 JSON）；
  与 ① 同属「读结果分层」主题可合并立项。

## 积极信号（无需动作）

- 单程序子调用 1.3 个（编排未失控）；lib.define 未滥用；并发纪律良好。
- 串行化自动执行（写路径 7 次）；denied 7 次全为权限形态（预期拦截）。
