## 优化线索（按痛点排序）

### ① 单行 425KB——收束行结构性膨胀
- 现象：messages.jsonl 2.5MB / 70 行（均值 36KB/行）；最大收束行 425KB
  含 13+ run_code 调用对（单对 arguments 0.2-1.3KB + result 5-9KB）。
- 根因：收束行 steps 携带整轮全部调用对（KV 前缀保真语义）。读操作
  （read/grep 的文件内容全文）对回放有价值但体积大头。
- 方向：steps 按工具类分层——写操作全量、读操作 result 降为摘要/偏移。
  动 KV 语义，需单独立项权衡（跨轮命中损失 vs 存储减半）。

### ② 失败形态集中——可擦除 TS 的 DX 税（纯收益，优先做）
- 8/14 失败 = 「程序体类型擦除失败 Expected ',', got 'ident'/'string
  literal'」——全部是模板串嵌套/含 \n 字面量被传输层转义破坏。占失败 2/3。
- 方向：worker 预检错误带【行列 + 最近 token + 修复建议】；SDK 投影
  （DEFAULT_GUIDANCE）加模板串转义显式示例；可选：程序体传入前服务端
  做常见转义形态探测告警。

### ③ edit 匹配失败退化为 pwsh——写路径成本隐性上升
- 现象：edit 218 次之外，pwsh 256 中相当部分是「读文件 + 行级替换」
  ——edit 的 old_string 在 CRLF/转义层消耗上反复失配（本会话 ≥6 次退路）。
- 方向：edit 失败信息附带【最接近的实际行内容 + 差异位置】；old_string
  对行尾差异做显式归一化提示（不静默模糊匹配——保留现有防错语义）。

### ④ subcalls.jsonl 1898KB——读操作结果全文在档
- 现象：782 子调用全文落盘（UI 回放档案语义），read 189 次的文件内容
  全量在内；已接近主文件体量。
- 方向：归档压缩 / UI 投影按需加载（偏移量记录而非全量 JSON）；
  与 ① 同属「读结果分层」主题可合并立项。

## 积极信号（无需动作）

- 单程序子调用 1.3 个（编排未失控）；lib.define 未滥用；并发纪律良好。
- 串行化自动执行（写路径 7 次）；denied 7 次全为权限形态（预期拦截）。

## 建议优先级

②（DX 税，纯收益）→ ③（edit 匹配改进）→ ①+④（读结果分层，立项权衡）

## 失败形态重构（82 条细分——本次最重要的发现）

### Ⓐ pwsh「命令退出码 1」47 条 = 全部失败的一半以上
- **其中绝大多数是 vitest 红灯（70 次 pwsh 里失败密集）**——这是测试驱动
  开发的【预期反馈环】不是工具错误。run_code 的 ok/err 统计把「命令语义
  失败」与「工具链路失败」混算，err 数字本身不可直接引用。
- **改进方向：pwsh 结果把退出码与语义分类分离**——exitCode != 0 且
  stdout 有结构化内容（vitest reporter 输出）→ 标记「反馈型结果」而非
  error；真转义/语法错（ParserError/SyntaxError）才是 error。SDK 文档
  同步教模型区分两者。

  通道**，这是 edit DX 失信的强信号。
- **改进方向（升级为高优先）：**
  1. edit 写回时强制归一化行尾（检测 \r\r\n 形态并在写入前修复——治损伤源）；
  2. 失配 error 附【文件实际行尾形态 + old_string 期望形态】（一行诊断顶
     十次盲试）；

## 机制性发现（本次唯一价值——两条 SDK 契约实证）

### Ⓐ lib.define 不接受「函数对象」，只接受源码字符串
- 现象：`lib.define('pick', (obj, keys) => ...)` 后 `lib.resolve('pick')` 拿到
  的非可调用值，使用即 `pick is not a function`；同程序内前两次子调用
  （list_tools / glob）正常完成——**失败在程序体，不在工具链路**。
- 结论：SDK 文档「value = 函数源码或含 return 的程序体字符串」是**硬约束**
  （须经序列化跨程序传递）；正确写法
  `lib.define('pick', '(obj, keys) => keys.map(...).join(" | ")')`。
- 改进方向（低成本）：`lib.define` 收到非字符串/非源码 value 时**当场抛带
  指引的错误**（"value 须为源码字符串——函数对象无法跨程序传递"），而非留
  到 resolve/调用点才炸；`lib.resolve` 的类型投影标注返回形状。

### Ⓑ load_skill 是「注入型」工具，返回值只是回执
- 现象：`tools.load_skill({name})` 的 output 仅 181 字符 4 字段
  （name / scope / baseDir / status:"injected"）——**正文不在返回值里**，
  由注入机制随后续轮次进入上下文（本轮实测：正文在下一轮作为系统提醒送达）。
- 推论：程序化模式下「把技能正文当数据处理」（抽清单、比对路径）拿不到
  正文——须改用 read 技能目录文件，或把技能消费留在推理层；
  `status:"injected"` 是程序内唯一可用的成功信号。

## 积极信号

- 用户显式「不要并行」被严格遵守（三次 run_code 串行、无并发提交）；
  程序化模式默认串行，本会话是其受控验证。
