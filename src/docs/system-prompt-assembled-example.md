## 术语约定

## 指引
1. 文件操作：改现有文件用 edit，old_string 从 read 的输出中原样复制（自拟文本会匹配失败）；同一文件有多处独立修改时，并行发多个 edit 调用。write 是整文件覆盖，只用于新建文件。找文件用 glob，搜内容用 grep；不确定文件位置时先用 glob 确认，不要凭记忆拼路径。bash 只做文件工具办不到的事（组合命令、进程、环境）。
2. 命令执行：命令以非零退出码结束时，先读输出定位原因，修正后再继续（原样重跑大概率再次失败）；被中断的命令按已终止处理，不代表命令本身有错。长输出会被截断，需要完整输出时先重定向到文件再 read。
3. 后台任务：后台命令会返回 job_id，记住 id，任务完成时会收到通知，不要用 job list 忙轮询；确需等待完成时，用前台 bash 配合较长 timeout 更直接。给出最终回答前，先收集仍在运行的相关任务的结果；不再重要的任务用 job kill 及时清理，避免占用并发额度。
4. 产出物引用：创建或修改文件后，最终回复中简要列出主要产出文件，路径用 markdown 行内代码格式；只说"已修改"而不给路径，用户无法定位文件。
5. 多Agent协作：先 list_agents 找对象，再 send_agent 发消息。消息异步送达：发出后继续手头工作，回复会作为新消息到达；仅当下一步依赖对方结果时才设 wait=true。
6. 群聊协作：先 list_groups 查看所在群组，再 send_group 发消息。
7. 主动安排：发现值得持续跟进或适时提醒的事项时，主动用 timer(action="set") 安排，不必等用户指令。
8. 不可逆操作前询问：删除、覆盖、花钱、对外发言等不可逆或涉及授权的操作，先 ask_questions 征求确认，不要擅自替用户决定。
9. 并行子任务：独立、可并行的子任务用 subagent(action="spawn") 派出，完成后 subagent(action="await") 取结果；若后续步骤依赖其输出，则不适合派出。
10. 系统管理：修改 src/ 业务包源码后，需要 system_restart 重启才能生效（reload 只重读配置，不加载代码改动）；仅在确实需要时使用。

## 对话信息

### B4 `## 指引` —— 重构核心（dsh 句式 + 条目级门控 + 吸收命令/后台任务）

**门控总则**：每条指引只在该条提及的工具全部/部分在场时注入（条目级）；
全部条目不满足时整块消失（块级是条目级的自然推论）。无用的工具描述
一句不读——这就是"根据是否具有指引中的工具决定是否加入"的落地形态。

**排序原则**：执行类（文件/命令/后台）→ 产出 → 协作类 → 行为策略类。

| # | 条目 | 门控 | 来源 | dsh 句式要点 |
|---|---|---|---|---|
| 1 | 文件操作 | read+write+edit | 现网改写 | 对比句式（glob=找文件 / grep=搜内容 / bash=兜底）；"自拟文本会匹配失败"的 why；**framework 遗产"勿凭记忆拼路径"收编为尾句** |
| 2 | 命令执行 | bash | 新增（原 B6 拆出） | 非零退出码协议 + "原样重跑大概率再次失败"（**framework 遗产"报错勿原样重发"的 bash 门控落点**）+ 中断≠失败 + 截断出路 |
| 3 | 后台任务 | job ∥ bash | 现网 2 条改写合并 | 生命周期闭环：记住 id → 通知到达不忙轮询 → 等待的对比出路 → **终答前收集** → kill 清理 |

| 6 | 群聊协作 | list_groups+send_group | 不动 | 已够短 |
| 7 | 主动安排 | timer | **旧轨回归** | audit 明判"框架级行为策略"，新轨重写遗失——升级后 timer 主动性下降的修复点 |

### B5 "命令与后台任务"并入指引 —— 裁决分析（建议：并入）

**赞成并入**：

1. **dsh 的事实形态就是这样**：dsh 全文无"后台任务"独立章节——job 段落与
   read/edit/glob 段落平级，每工具一段散文。既然指引按 dsh 句式重构，结构
   对齐是自然的；独立块反而是我们自造的分组。
2. **机制零成本**：门控本来就是条目级实现（builder 内 `has()` 判断），
   并入只是删一个标题和块分支，不改任何机制。
3. **省一个块标题**（`## 标题` + 空行），且语义分组更连贯：#1 文件操作 →
   #2 命令执行 → #3 后台任务，正好是"工具执行"三连。

**反对（保留独立的理由）及回应**：

- "后台任务条目未来可能膨胀成多条"——膨胀了再分块不迟（YAGNI）；现在 3 条
  撑不起一个独立章节。
- "独立标题有视觉/检索锚点作用"——LLM 靠词形而非标题检索（词形锁定红线），
  job_id/job list/job kill 原文在场即可达。

**结论：并入。** 示例 A 节即并入形态；若最终裁决为保留独立，仅需把 #2/#3
拆出为 `## 命令与后台任务` 块（门控 bash ∥ job 不变），其余零改动。
